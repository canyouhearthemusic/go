# Каналы: внутреннее устройство

Разбор по дереву Go 1.25 (`src/runtime/chan.go`, `src/runtime/select.go`), поведение проверено на Go 1.26.1 darwin/arm64.
Практическая сторона — паттерны, утечки, `select`, `context` — в [channels_guide.md](channels_guide.md).

## Терминология

- **`hchan`** — структура канала в рантайме. Переменная типа `chan T` — это **указатель** на `hchan`.
- **Буфер (`buf`)** — кольцевой массив на `dataqsiz` элементов. У небуферизованного канала его нет (`dataqsiz == 0`).
- **`sudog`** — обёртка над заблокированной горутиной, стоящей в очереди канала. Хранит указатель на элемент, который она шлёт или куда принимает.
- **`recvq` / `sendq`** — FIFO-очереди (`waitq`) ждущих горутин.
- **Прямая передача (direct send/recv)** — значение копируется из стека одной горутины прямо в стек другой, минуя буфер.
- **`gopark` / `goready`** — усыпление и пробуждение горутины планировщиком.
- **Write barrier (барьер записи)** — код, который рантайм вставляет вокруг записи указателя, чтобы GC не потерял объект.

## Структуры — `chan.go:34`

```go
type hchan struct {
    qcount   uint           // сколько элементов сейчас в буфере
    dataqsiz uint           // размер кольцевого буфера (0 = небуферизованный)
    buf      unsafe.Pointer // массив из dataqsiz элементов
    elemsize uint16         // отсюда лимит: элемент < 64 КБ
    closed   uint32         // 0 = открыт, 1 = закрыт
    timer    *timer         // непусто только у каналов таймеров
    elemtype *_type
    sendx    uint           // индекс записи в кольце
    recvx    uint           // индекс чтения из кольца
    recvq    waitq          // очередь ждущих получателей
    sendq    waitq          // очередь ждущих отправителей
    bubble   *synctestBubble // для testing/synctest
    lock     mutex          // ОДИН мьютекс на весь канал
}

type waitq struct {  // двусвязный FIFO-список sudog
    first *sudog
    last  *sudog
}
```

Ключевое: **весь канал защищён одним `lock mutex`**. Канал — не lock-free структура, а «мьютекс + две очереди + кольцевой буфер». Вся сложность — в аккуратной передаче значений под этим локом.

Инварианты из шапки файла (`chan.go:9`):

- хотя бы одна из `sendq`/`recvq` всегда пуста (исключение — одна горутина в `select`, ждущая на одном канале и на отправку, и на приём);
- для буферизованных: `qcount > 0` ⇒ `recvq` пуста; `qcount < dataqsiz` ⇒ `sendq` пуста.

То есть «в буфере есть данные, и при этом кто-то ждёт приёма» невозможно: получателю отдали бы сразу.

```
hchan (буферизованный, cap=4, qcount=2)
┌──────────────┐        buf (кольцо на 4)
│ qcount = 2   │        ┌────┬────┬────┬────┐
│ dataqsiz = 4 │        │ ?? │ A  │ B  │ ?? │
│ buf ─────────┼───────→└────┴────┴────┴────┘
│ sendx = 3    │           0    1    2    3
│ recvx = 1    │           ↑recvx        ↑sendx
│ recvq: []    │
│ sendq: []    │
└──────────────┘
```

## Создание — `makechan`, `chan.go:75`

```go
func makechan(t *chantype, size int) *hchan {
    if elem.Size_ >= 1<<16 { throw("makechan: invalid channel element type") }
    mem := elem.Size_ * size            // с проверкой переполнения
    switch {
    case mem == 0:           // небуферизованный ИЛИ элемент нулевого размера
        c = mallocgc(hchanSize, nil, true)
        c.buf = c.raceaddr()
    case !elem.Pointers():   // элементы без указателей → hchan и buf одной аллокацией
        c = mallocgc(hchanSize+mem, nil, true)
        c.buf = add(unsafe.Pointer(c), hchanSize)
    default:                 // элементы с указателями → buf отдельно, чтобы GC его сканировал
        c = new(hchan)
        c.buf = mallocgc(mem, elem, true)
    }
    ...
}
```

- Ограничение на размер элемента ловит ещё компилятор: `make(chan [70000]byte)` — ошибка сборки `channel element type too large (>64kB)`. Обходится указателем на структуру.
- Слишком большой буфер — паника `makechan: size out of range`.
- Канал всегда живёт в куче: на него ссылаются чужие горутины, escape analysis его не удержит на стеке.
- Отдельного «освобождения» канала нет: закрывать канал ради GC не нужно, недостижимый канал собирается как обычный объект.

## Send — `chansend`, `chan.go:176`

`ch <- x` компилируется в `chansend1(c, &x)` → `chansend(c, ep, block=true, pc)`.

### 0. nil-канал

```go
if c == nil {
    if !block { return false }   // в select ветка просто не выбирается
    gopark(nil, nil, waitReasonChanSendNilChan, traceBlockForever, 2)
    throw("unreachable")
}
```

Отправка в nil-канал паркует горутину **навсегда**, без всякой очереди: разбудить её некому. В стектрейсе это видно как `goroutine 1 [chan send (nil chan)]`.

### 1. Быстрый путь без лока — `chan.go:213`

```go
if !block && c.closed == 0 && full(c) {
    return false
}
```

Это для `select` с `default`. Два невыровненных чтения слова без лока — и в комментарии рантайма объяснено, почему это корректно: закрытый канал не может снова стать «готовым к отправке», поэтому даже если канал закрыли между двумя чтениями, существовал момент, когда он был одновременно не закрыт и не готов. Мы делаем вид, что наблюдали именно его.

`full(c)` (`chan.go:146`) — тоже одно чтение: для небуферизованного это `c.recvq.first == nil`, для буферизованного `c.qcount == c.dataqsiz`.

### 2. Лок и проверка закрытия

```go
lock(&c.lock)
if c.closed != 0 {
    unlock(&c.lock)
    panic(plainError("send on closed channel"))
}
```

### 3. Есть ждущий получатель → прямая передача

```go
if sg := c.recvq.dequeue(); sg != nil {
    send(c, sg, ep, func() { unlock(&c.lock) }, 3)
    return true
}
```

`send` (`chan.go:318`) копирует значение **из стека отправителя прямо в стек получателя** через `sendDirect`, ставит `sg.success = true` и будит получателя через `goready`. Буфер не задействован вообще — даже у буферизованного канала. Это самый быстрый путь.

### 4. Есть место в буфере → кладём в кольцо

```go
if c.qcount < c.dataqsiz {
    qp := chanbuf(c, c.sendx)
    typedmemmove(c.elemtype, qp, ep)
    c.sendx++
    if c.sendx == c.dataqsiz { c.sendx = 0 }   // кольцо
    c.qcount++
    unlock(&c.lock)
    return true
}
```

### 5. Места нет → в очередь и спать

```go
mysg := acquireSudog()
mysg.elem = ep          // указатель на значение в СТЕКЕ отправителя
mysg.g = gp
mysg.c = c
c.sendq.enqueue(mysg)
gp.parkingOnChan.Store(true)
gopark(chanparkcommit, unsafe.Pointer(&c.lock), waitReasonChanSend, traceBlockChanSend, 2)
KeepAlive(ep)
// проснулись
if !mysg.success {      // разбудил close, а не получатель
    panic(plainError("send on closed channel"))
}
```

Значение **не копируется никуда** — в `sudog` кладётся указатель на переменную в стеке спящей горутины. Забирать оттуда будет получатель. `gp.parkingOnChan` и `chanparkcommit` нужны, чтобы сжатие стека не переехало под ногами у чужой горутины, которая вот-вот запишет в этот стек.

### Приоритеты send

```
ch <- x:
  ├─ канал nil        → парк навсегда (в select — ветка не выбирается)
  ├─ канал закрыт     → PANIC "send on closed channel"
  ├─ есть получатель  → копия в его стек, минуя буфер, goready
  ├─ есть место в буф → положить в кольцо (sendx++)
  └─ иначе            → sudog в sendq, gopark
```

## Receive — `chanrecv`, `chan.go:524`

`v := <-ch` → `chanrecv1`; `v, ok := <-ch` → `chanrecv2`. Внутри одна функция, возвращающая `(selected, received)`.

### 0. nil-канал

Парк навсегда, `waitReasonChanReceiveNilChan`.

### 1. Быстрый путь без лока

```go
if !block && empty(c) {
    if atomic.Load(&c.closed) == 0 { return }   // открыт и пуст → мимо
    if empty(c) {
        if ep != nil { typedmemclr(c.elemtype, ep) }
        return true, false                      // закрыт и пуст → ноль, ok=false
    }
}
```

Здесь порядок чтений важен и оба чтения атомарные: переставь их местами — и гонка с `close` может дать неверный ответ «открыт и пуст» для канала, который закрыли и вычерпали.

### 2. Лок. Закрыт и пуст?

```go
lock(&c.lock)
if c.closed != 0 && c.qcount == 0 {
    unlock(&c.lock)
    typedmemclr(c.elemtype, ep)   // нулевое значение
    return true, false            // ok = false, НЕ паника
}
```

Если канал закрыт, но в буфере ещё есть данные — их сначала дочитывают.

### 3. Есть ждущий отправитель

```go
if sg := c.sendq.dequeue(); sg != nil {
    recv(c, sg, ep, func() { unlock(&c.lock) }, 3)
    return true, true
}
```

`recv` (`chan.go:702`) делает разное в зависимости от типа канала:

- **небуферизованный**: `recvDirect` — копия из стека отправителя прямо к получателю;
- **буферизованный** (а раз отправитель ждёт, буфер полон): элемент берётся из **головы** буфера и отдаётся получателю, а значение отправителя кладётся в **хвост**. Голова и хвост в полном кольце — это один и тот же слот, поэтому всё сводится к двум `typedmemmove` в один слот и сдвигу `recvx`/`sendx`. Порядок FIFO при этом сохраняется.

В обоих случаях отправитель будится через `goready`.

### 4. Есть данные в буфере

```go
if c.qcount > 0 {
    qp := chanbuf(c, c.recvx)
    if ep != nil { typedmemmove(c.elemtype, ep, qp) }
    typedmemclr(c.elemtype, qp)     // зачистить слот, иначе буфер держит объект живым
    c.recvx++
    if c.recvx == c.dataqsiz { c.recvx = 0 }
    c.qcount--
    unlock(&c.lock)
    return true, true
}
```

`typedmemclr` здесь не для порядка: без него прочитанный элемент остался бы в буфере и GC считал бы его живым.

### 5. Пусто → в очередь и спать

`sudog` в `recvq`, `gopark`. `mysg.elem` — адрес переменной получателя; писать туда будет отправитель или `closechan`.

### Приоритеты receive

```
<-ch:
  ├─ канал nil          → парк навсегда (в select — ветка не выбирается)
  ├─ закрыт и пуст      → нулевое значение, ok=false (НЕ паника)
  ├─ есть отправитель   → прямая передача (или голова буфера + его значение в хвост)
  ├─ есть данные в буф  → прочитать из кольца (recvx++), слот занулить
  └─ иначе              → sudog в recvq, gopark
```

## Прямая передача и GC — `sendDirect`, `chan.go:392`

```go
func sendDirect(t *_type, sg *sudog, src unsafe.Pointer) {
    dst := sg.elem
    typeBitsBulkBarrier(t, uintptr(dst), uintptr(src), t.Size_)
    memmove(dst, src, t.Size_)
}
```

Из комментария рантайма: приём и отправка на небуферизованном канале — **единственное место в Go, где одна работающая горутина пишет в стек другой работающей горутины**. GC исходит из того, что в стек пишет только его владелец, поэтому обычного `typedmemmove` тут мало (он вызывает `bulkBarrierPreWrite`, а тот рассчитан на кучу). Вместо этого вызываются `typeBitsBulkBarrier` + `memmove` напрямую.

Второй нюанс: как только `sg.elem` прочитан в локальную переменную, он перестаёт обновляться при копировании (сжатии) стека получателя — поэтому между чтением и использованием не должно быть точек вытеснения.

## Close — `closechan`, `chan.go:414`

```go
func closechan(c *hchan) {
    if c == nil { panic("close of nil channel") }
    lock(&c.lock)
    if c.closed != 0 { panic("close of closed channel") }
    c.closed = 1

    var glist gList
    for sg := c.recvq.dequeue(); sg != nil; sg = c.recvq.dequeue() {
        if sg.elem != nil { typedmemclr(c.elemtype, sg.elem) }  // отдать нулевое значение
        sg.success = false                                      // → ok == false
        glist.push(sg.g)
    }
    for sg := c.sendq.dequeue(); sg != nil; sg = c.sendq.dequeue() {
        sg.elem = nil
        sg.success = false                                      // → они паникнут
        glist.push(sg.g)
    }
    unlock(&c.lock)

    for !glist.empty() { goready(glist.pop(), 3) }   // будим уже без лока
}
```

Два момента реализации: горутины сначала собираются в список и будятся **после** снятия лока (иначе `goready` под локом канала может подвиснуть на сжатии стека), и `sg.success = false` — это единственный признак, по которому проснувшаяся горутина отличает «меня обслужили» от «канал закрыли».

| Операция | Результат |
|---|---|
| `close(nil)` | panic `close of nil channel` |
| `close` закрытого | panic `close of closed channel` |
| `send` в закрытый | panic `send on closed channel` |
| `recv` из закрытого | нулевое значение, `ok == false` |
| `recv` из закрытого с непустым буфером | сначала выдаются оставшиеся элементы |

## Кольцевой буфер: sendx / recvx

```
cap=4. Шлём A,B,C; читаем A; шлём D,E

[_,_,_,_]  sendx=0 recvx=0 qcount=0   старт
[A,_,_,_]  sendx=1         qcount=1   send A
[A,B,_,_]  sendx=2         qcount=2   send B
[A,B,C,_]  sendx=3         qcount=3   send C
[A,B,C,_]  sendx=3 recvx=1 qcount=2   recv → A  (слот 0 зануляется)
[_,B,C,D]  sendx=0(wrap)   qcount=3   send D
[E,B,C,D]  sendx=1         qcount=4   send E    ← слот 0 переиспользован
```

`sendx == recvx` означает и «пусто», и «полно» — поэтому нужен отдельный `qcount`.

## Очередь ожидания: `waitq`

`enqueue` (`chan.go:872`) добавляет в хвост, `dequeue` (`chan.go:886`) снимает с головы — честный **FIFO**. Проверяется наблюдением: пять горутин, вставших в `sendq` по очереди, обслуживаются в том же порядке.

В `dequeue` есть одна тонкость. Горутина, ставшая в очередь из `select`, могла быть уже разбужена другой веткой:

```go
if sgp.isSelect {
    if !sgp.g.selectDone.CompareAndSwap(0, 1) {
        continue   // гонку за эту горутину мы проиграли — берём следующую
    }
}
```

Поэтому `sudog` в очереди не гарантирует, что его горутина ещё доступна.

`sudog` берутся из пулов (`acquireSudog`/`releaseSudog`): кэш на P плюс центральный список, так что блокирующие операции на канале обычно не аллоцируют — в бенчмарках видно `0 allocs/op`.

## `len` и `cap` — `chan.go:818`, `chan.go:835`

```go
func chanlen(c *hchan) int { if c == nil { return 0 }; ...; return int(c.qcount) }
func chancap(c *hchan) int { if c == nil { return 0 }; ...; return int(c.dataqsiz) }
```

- Оба безопасны для nil-канала и возвращают 0.
- Читаются **без лока**: результат мгновенно устаревает. На нём нельзя строить логику вида «если `len(ch) < cap(ch)`, то отправка не заблокируется».
- У каналов таймеров (`c.timer != nil`) реализация буферизованная, но наружу `len` и `cap` показывают 0 — чтобы рантайм мог «отменить» уже положенное значение незаметно для пользователя. Проверено: `cap(time.After(time.Hour)) == 0`.

## Select — `select.go`

### Что делает компилятор (`cmd/compile/internal/walk/select.go`)

До рантайма доходит не всякий `select`:

| Форма | Во что превращается |
|---|---|
| `select {}` | вызов `block()` — парк навсегда |
| один case без default | обычный `ch <- x` / `<-ch` |
| один case + `default` | `if selectnbsend(c, &v) {...} else {...}` или `selectnbrecv` (`chan.go:784`, `chan.go:804`) — то есть `chansend`/`chanrecv` с `block=false` |
| всё остальное | `selectgo` |

Поэтому «неблокирующая отправка» через `select`+`default` не платит за `selectgo` вообще.

### `selectgo`, `select.go:122`

Компилятор передаёт массив `scase` (сначала все send-ветки, потом все recv-ветки) и место под два массива индексов.

**1. Перемешивание.** `pollorder` — случайная перестановка веток (алгоритм Фишера–Йетса на `cheaprandn`, `select.go:191`). Отсюда и берётся равномерный выбор между готовыми ветками. Измерено на 30 000 выборов из трёх готовых: 10063 / 10151 / 9786.

**2. Порядок блокировок.** `lockorder` — те же ветки, отсортированные **по адресу `hchan`** (пирамидальная сортировка, `select.go:208`). Все `select` в программе берут локи каналов в одном и том же глобальном порядке, поэтому два `select` на пересекающихся наборах каналов не могут заклиниться друг о друга. Дубликаты каналов схлопываются при снятии локов (`selunlock`).

**3. Проход 1** (`select.go:270`) — по `pollorder`, под всеми локами: ищем ветку, которую можно выполнить прямо сейчас (есть партнёр в очереди, есть данные/место в буфере, канал закрыт). Нашли — выполняем и выходим. Не нашли и есть `default` — снимаем локи, уходим в `default`.

**4. Проход 2** (`select.go:309`) — встаём в очередь **на все** каналы сразу: по `sudog` на ветку, все связаны через `gp.waiting`, затем один `gopark` с причиной `select`.

**5. Проход 3** — после пробуждения: определяем, какая ветка сработала (`gp.param` указывает на выигравший `sudog`), и **выписываемся из всех остальных очередей**. Проигравшие `sudog` возвращаются в пул.

Отсюда стоимость: `select` из двух веток — 43 нс против 18 нс у прямой операции на буферизованном канале (замер ниже). Каждая ветка — это `sudog`, постановка в очередь и снятие с неё.

### Ограничения

Число веток ограничено 65536 (`cas1 := (*[1 << 16]scase)(...)`). Ветки с `nil`-каналом просто исключаются из `pollorder`/`lockorder` — это и есть механизм «выключения» ветки.

## Обнаружение дедлока

Если **все** горутины программы спят и ни одна не может быть разбужена, планировщик печатает `fatal error: all goroutines are asleep - deadlock!` и валит процесс. Это не паника — её нельзя перехватить `recover`.

Причина парковки видна прямо в стектрейсе — она берётся из `waitReason`:

```
goroutine 1 [chan receive]:
goroutine 1 [chan send (nil chan)]:
goroutine 7 [select]:
```

Важное ограничение: детектор срабатывает, только когда спят **все**. Если хоть одна горутина крутится (или ждёт сети/таймера), заблокированные навсегда горутины просто остаются висеть — это и есть утечка горутин, никакой ошибки не будет.

| `mu.Lock(); x++; mu.Unlock()` | 2.6 |
| send+recv в одной горутине на `cap=1` | 18.3 |
| send в буферизованный (`cap=64`), приём в другой горутине | 23.2 |
| send в небуферизованный, приём в другой горутине | 96.1 |
| `select` из двух веток | 43.4 |

Что из этого следует: канал — не замена мьютексу для защиты состояния (разница в 7–40 раз), а механизм передачи владения и уведомления. Небуферизованный канал дороже буферизованного примерно вчетверо, потому что каждая передача — это гарантированное переключение горутин.

## Шпаргалка

| Свойство | Значение |
|---|---|
| Что в переменной | указатель на `hchan` |
| Синхронизация | один `mutex` на весь канал |
| Буфер | кольцевой массив `dataqsiz`, индексы `sendx`/`recvx` |
| Небуферизованный | `dataqsiz == 0`, передача стек→стек |
| Самый быстрый путь | партнёр уже ждёт → копия напрямую, минуя буфер |
| Блокировка | `sudog` в `sendq`/`recvq` + `gopark` |
| Порядок пробуждения | FIFO |
| `select` | случайный `pollorder`, локи по адресу канала, `sudog` на каждую ветку |
| Лимит размера элемента | 64 КБ (ошибка компиляции) |
| Лимит веток в `select` | 65536 |
| send в закрытый | panic |
| recv из закрытого | нулевое значение, `ok=false` |
| `close(nil)` / `close` закрытого | panic |
| send/recv в nil | парк навсегда |
| `len`/`cap` | `qcount`/`dataqsiz`, читаются без лока |
