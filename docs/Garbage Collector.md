## TL;DR — характеристика одним абзацем

GC в Go — это **конкурентный (concurrent), трёхцветный (tri-color), mark-and-sweep** сборщик с **write barrier**, работающий **параллельно с программой**. Он **не перемещающий (non-moving)** и **не поколенческий (non-generational)**. Главная цель дизайна — **низкие паузы** (single-digit миллисекунды и меньше), а не максимальная пропускная способность. Подтверждается комментарием в [mgc.go:8](vscode-webview://134g8j27pubsrs9od3idlmo4823tfa8108pm0gii6k1he6r1s7oq/src/runtime/mgc.go#L8): _"It is a concurrent mark and sweep that uses a write barrier."_

---

## Терминология

- **Мутатор (mutator):** твоя программа (горутины). Названа так, потому что «мутирует» граф объектов, пока GC его обходит.
- **Roots (корни):** отправные точки обхода — стеки горутин, глобальные переменные, регистры.
- **Mark (маркировка):** обход графа достижимых объектов от корней, пометка «живых».
- **Sweep (очистка):** освобождение памяти объектов, которых маркировка не пометила.
- **Трёхцветная абстракция:** способ описать прогресс маркировки тремя «цветами» (ниже).
- **Write barrier (барьер записи):** код, который рантайм вставляет перед записью указателя; нужен, чтобы маркировка оставалась корректной, пока мутатор меняет граф.
- **STW (Stop-The-World):** момент, когда **все** горутины приостановлены. В Go он очень короткий (микросекунды), не на всю сборку.
- **Pacer:** «кардиостимулятор» — компонент, решающий **когда** запускать сборку и сколько CPU ей выделить.

## Трёхцветный алгоритм

Каждый объект мысленно окрашен в один из трёх цветов:

|Цвет|Значение|
|---|---|
|⚪ **Белый**|ещё не обработан. В конце сборки все белые = мусор, их свипают.|
|⚫ **Серый**|помечен как живой, но его указатели **ещё не просканированы**. Стоит в очереди работы.|
|⬛ **Чёрный**|живой и полностью просканирован (все исходящие указатели обработаны).|

Процесс:

```
1. Все объекты белые. Корни красим в серый.
2. Берём серый объект → сканируем его указатели:
     каждый указуемый белый объект красим в серый.
   Сам объект становится чёрным.
3. Повторяем, пока серых не останется.
4. Все оставшиеся белые объекты недостижимы → свипаем.
```

**Ключевой инвариант (tri-color invariant):** чёрный объект **никогда не должен указывать прямо на белый** (без промежуточного серого). Если это нарушить во время конкурентной работы — живой объект ошибочно соберут.

## Зачем нужен write barrier

Проблема: GC сканирует граф, а мутатор **одновременно** его меняет. Классический сценарий потери объекта:

```
1. GC уже сделал объект A чёрным (просканировал).
2. Мутатор: A.ptr = C   (A теперь указывает на белый C)
3. Мутатор: B.ptr = nil  (единственная другая ссылка на C исчезла)
4. C остался белым, но он живой → GC его соберёт. БАГ.
```

**Write barrier** перехватывает шаг 2: при записи указателя он **затеняет (shade)** объект — красит C в серый, чтобы тот не пропал. В Go используется **гибридный барьер (Dijkstra + Yuasa)**, добавленный в Go 1.8 — он позволил **не делать повторного STW-сканирования стеков** в конце. Из [mgc.go:41](vscode-webview://134g8j27pubsrs9od3idlmo4823tfa8108pm0gii6k1he6r1s7oq/src/runtime/mgc.go#L41): _"The write barrier shades both the [old and new] pointers."_

Барьер **включён только во время фазы маркировки** [mgc.go:259](vscode-webview://134g8j27pubsrs9od3idlmo4823tfa8108pm0gii6k1he6r1s7oq/src/runtime/mgc.go#L259):

```go
writeBarrier.enabled = gcphase == _GCmark || gcphase == _GCmarktermination
```

Вне сборки записи указателей идут без накладных расходов.

## Фазы цикла GC

Рантайм держит глобальное состояние `gcphase` [mgc.go:251](vscode-webview://134g8j27pubsrs9od3idlmo4823tfa8108pm0gii6k1he6r1s7oq/src/runtime/mgc.go#L251):

```go
_GCoff             // GC не идёт; фоновый sweep; write barrier ВЫКЛ
_GCmark            // маркировка: аллоцируем «чёрным», write barrier ВКЛ
_GCmarktermination // завершение маркировки: write barrier ВКЛ
```

### Полный цикл по шагам

```
   [_GCoff]  программа работает, фоновый sweep предыдущего цикла
       │
       │  pacer решил: пора (heap дорос до цели)
       ▼
1. Sweep Termination  ──STW (коротко)──
       │  завершить свип прошлого цикла, подготовиться
       ▼
2. [_GCmark]  ◀═══ КОНКУРЕНТНО с программой ═══▶
       │  - включён write barrier
       │  - новые аллокации сразу «чёрные» (allocate black)
       │  - фоновые mark-воркеры (~25% CPU) обходят граф
       │  - mark assist: горутина, много аллоцирующая, ПОМОГАЕТ маркировать
       ▼
3. Mark Termination  ──STW (коротко)──
       │  [_GCmarktermination] добить остатки маркировки, выключить барьер
       ▼
4. [_GCoff] + Sweep  ◀═══ КОНКУРЕНТНО ═══▶
       │  свип идёт лениво/фоном: память освобождается по мере надобности
       ▼
   обратно в [_GCoff]
```

**Важно:** STW в Go — это только короткие переходы (шаги 1 и 3), обычно **десятки-сотни микросекунд**. Сама маркировка и свип идут **параллельно** с программой. Это и есть причина низких пауз.

## Кто делает работу: воркеры и assist

Цель — отдать GC примерно **25% CPU** [mgcpacer.go:39](vscode-webview://134g8j27pubsrs9od3idlmo4823tfa8108pm0gii6k1he6r1s7oq/src/runtime/mgcpacer.go#L39):

```go
gcBackgroundUtilization = 0.25
```

Три типа исполнителей маркировки:

1. **Dedicated workers** — выделенные горутины, маркируют на полную.
2. **Fractional workers** — добивают долю до 25%, когда dedicated не делятся нацело на число P.
3. **Mark assist** — самое важное для понимания пауз: если горутина аллоцирует быстрее, чем GC успевает маркировать, **её саму** заставляют помогать маркировке пропорционально аллокации. Это «налог на аллокацию» — он не даёт heap убежать вперёд и гарантирует, что сборка завершится.

> Практический вывод: если видишь в профиле много времени в `gcAssistAlloc` — программа аллоцирует слишком агрессивно, GC не успевает, и горутины тормозят, помогая ему.

## Pacer — когда запускается сборка

Решающий параметр — **`GOGC`** (по умолчанию **100**).

**Правило:** сборка стартует, когда heap вырос на `GOGC%` относительно размера живого heap после прошлой сборки.

```
GOGC=100 (дефолт):
  после сборки живёт 100 MB
  → следующая сборка стартует, когда heap дорастёт до ~200 MB
  (цель = живой_heap * (1 + GOGC/100))
```

|GOGC|Поведение|
|---|---|
|`100`|дефолт: heap может удвоиться между сборками|
|Больше (`200`, `500`)|реже сборки, больше памяти, выше throughput, меньше CPU на GC|
|Меньше (`50`, `20`)|чаще сборки, меньше памяти, больше CPU на GC|
|`off`|GC выключен полностью (осторожно!)|

### GOMEMLIMIT (с Go 1.19)

**Мягкий лимит памяти**. По умолчанию выключен (`math.MaxInt64`). Когда задан, GC начинает работать **чаще**, чтобы удержать общее потребление под лимитом — даже если по `GOGC` ещё рано.

```bash
GOMEMLIMIT=4GiB ./app          # держать память под ~4 GiB
GOGC=off GOMEMLIMIT=4GiB ./app # частая идиома: GC только по лимиту памяти
```

Зачем: защита от OOM в контейнерах. `GOGC` реагирует на **относительный** рост, `GOMEMLIMIT` — на **абсолютный** потолок. Часто используют вместе.

## Чего Go GC НЕ делает (важные отрицания)

- **Не перемещает объекты (non-moving).** Адрес объекта стабилен → можно безопасно держать указатели, в т.ч. в C через cgo. Цена — фрагментация (решается size-class аллокатором, как мы видели у слайсов с `roundupsize`).
- **Не поколенческий (non-generational).** Нет разделения на young/old gen с отдельными minor/major сборками. Каждая сборка обходит весь живой граф. (Исторически были эксперименты с generational, но не прижились — escape analysis + стек-аллокация уже снимают много короткоживущего мусора.)
- **Не компактизирующий.** Связано с non-moving.
- **Не реалтайм с жёсткими гарантиями** — паузы малы статистически, но это не hard-real-time.

## Green Tea GC (новинка, дефолт в 1.26)

В go1.26.4 фаза **маркировки** по умолчанию использует новый алгоритм **Green Tea** [exp.go:88](vscode-webview://134g8j27pubsrs9od3idlmo4823tfa8108pm0gii6k1he6r1s7oq/src/internal/buildcfg/exp.go#L88) (`GreenTeaGC: true` в baseline).

- **Проблема старого маркера:** обход графа «по одному указателю» прыгает по случайным адресам — плохо для кэша (та же беда, что у старой мапы с overflow-цепочками).
- **Идея Green Tea:** группировать работу **по спанам/страницам памяти**, сканировать локально и параллелиться лучше → меньше промахов кэша, выше throughput маркировки.
- Это **не отдельный GC**, а другой алгоритм только марк-фазы. Свип, барьеры, pacer — те же.
- Откатить: `GOEXPERIMENT=nogreenteagc go build`.

---

## Что отдаёт память обратно ОС

После свипа память не сразу возвращается ОС — она помечается как **scavengeable** и отдаётся фоновым **scavenger**'ом постепенно (через `madvise`). `GOMEMLIMIT` влияет на агрессивность возврата. Поэтому RSS процесса падает не мгновенно после освобождения.

## Как наблюдать и тюнить

```bash
GODEBUG=gctrace=1 ./app     # строка на каждую сборку: паузы, heap, CPU
GOGC=200 ./app              # реже сборки
GOMEMLIMIT=2GiB ./app       # потолок памяти
```

В коде:

```go
runtime.GC()                 // форсировать сборку (обычно НЕ нужно)
debug.SetGCPercent(200)      // = GOGC программно
debug.SetMemoryLimit(2<<30)  // = GOMEMLIMIT программно
runtime.ReadMemStats(&m)     // детальная статистика heap
```

Пример строки `gctrace`:

```
gc 14 @2.3s 1%: 0.018+1.2+0.004 ms clock, 0.30+0.5/1.1/0+0.06 ms cpu, 8->9->5 MB, 9 MB goal, 16 P
                     │STW │конк│STW                          │heap до→после марк→живой│ цель│
```

## Практические выводы (что реально влияет на GC)

1. **Меньше аллокаций → меньше работы GC.** Главный рычаг. Помогают: переиспользование (`sync.Pool`), предвыделение слайсов с `cap`, отказ от лишних указателей.
2. **Escape analysis** решает, попадёт ли значение в heap или останется на стеке. То, что не «убегает» (`go build -gcflags=-m`), вообще не нагружает GC.
3. **Указатели дороги для GC.** Структура без указателей (`noscan`) не сканируется при маркировке. `[]int` дешевле для GC, чем `[]*T`. (Это тот же `!elem.Pointers()`-флаг, что мы видели в мапах и каналах.)
4. **`GOGC`/`GOMEMLIMIT`** — настраивай под профиль: latency-sensitive сервис vs batch-обработка.
5. **`mark assist` в профиле** = программа аллоцирует быстрее, чем GC успевает. Сигнал снижать аллокации.

## Шпаргалка одним взглядом

|Свойство|Go GC|
|---|---|
|Тип|конкурентный tri-color mark-and-sweep|
|Перемещающий|❌ нет (non-moving)|
|Поколенческий|❌ нет (non-generational)|
|Барьер|гибридный write barrier (Dijkstra + Yuasa), только в фазе mark|
|STW|только короткие переходы (мкс), не вся сборка|
|Параллелизм|mark и sweep идут вместе с программой|
|Бюджет CPU|~25% (`gcBackgroundUtilization = 0.25`)|
|Триггер|heap вырос на `GOGC`% (дефолт 100)|
|Лимит памяти|`GOMEMLIMIT` (мягкий, дефолт выкл)|
|Цель дизайна|низкие паузы, а не max throughput|
|Маркировка в 1.26|Green Tea (по спанам, дефолт)|

|Фаза|STW?|Барьер|Что происходит|
|---|---|---|---|
|Sweep termination|да (коротко)|—|закрыть прошлый свип|
|Mark|нет|вкл|конкурентная маркировка + assist|
|Mark termination|да (коротко)|вкл|добить маркировку|
|Sweep (_GCoff)|нет|выкл|ленивое освобождение памяти|
