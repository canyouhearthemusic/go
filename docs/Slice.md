# Срезы: внутреннее устройство

Разбор по дереву Go 1.25 (`src/runtime/slice.go`), поведение проверено на Go 1.26.1 darwin/arm64.
Практическая сторона — ловушки, паттерны, пакет `slices` — в [slices_guide.md](slices_guide.md).

## Терминология

- **Backing array (базовый массив)** — непрерывный кусок памяти, где лежат элементы. Срез им **не владеет монопольно**: несколько срезов могут смотреть в один и тот же массив.
- **Slice header (заголовок)** — структура из трёх полей (`array`, `len`, `cap`). Именно она копируется при присваивании и передаче в функцию. Данные при этом не копируются.
- **len** — сколько элементов доступно: `s[0]` … `s[len-1]`.
- **cap** — сколько элементов помещается в backing array, считая от `array`, без новой аллокации.
- **Реаллокация (рост)** — выделение нового, большего массива и копирование в него старых данных.
- **Size class (класс размера)** — фиксированный размер блока, которыми оперирует аллокатор Go. Запрос округляется вверх до ближайшего класса.
- **Escape analysis (анализ убегания)** — проход компилятора, который решает, может ли значение жить на стеке или обязано уехать в кучу.

## Slice header — `src/runtime/slice.go:15`

```go
type slice struct {
    array unsafe.Pointer // указатель на начало backing array
    len   int            // длина
    cap   int            // ёмкость
}
```

Три машинных слова: **24 байта на 64-битной платформе** (`unsafe.Sizeof(s) == 24`), **12 байт на 32-битной** (386, arm). Когда пишешь `s2 := s1` или передаёшь срез в функцию — копируются только эти три поля.

```
s := []int{10, 20, 30}   // len=3, cap=3

slice header              backing array
┌─────────┐               ┌────┬────┬────┐
│ array ──┼──────────────→│ 10 │ 20 │ 30 │
│ len = 3 │               └────┴────┴────┘
│ cap = 3 │                idx:  0    1    2
└─────────┘
```

**nil-срез** — это header, у которого `array == nil, len == 0, cap == 0`. Никакой отдельной «пустой» структуры в рантайме нет: `s == nil` — это буквально проверка указателя.

Доступ к полям заголовка из обычного кода: `unsafe.SliceData(s)` даёт `array`, `unsafe.Slice(ptr, n)` собирает заголовок обратно. `reflect.SliceHeader` устарел и небезопасен — не используй.

## Создание

### `make([]T, len, cap)` → `makeslice` — `slice.go:101`

```go
func makeslice(et *_type, len, cap int) unsafe.Pointer {
    mem, overflow := math.MulUintptr(et.Size_, uintptr(cap))
    if overflow || mem > maxAlloc || len < 0 || len > cap {
        // len сообщается в ошибке даже когда виноват cap: см. issue 4085
        panicmakeslicelen() / panicmakeslicecap()
    }
    return mallocgc(mem, et, true)   // cap*size байт, обнулённых
}
```

Память выделяется под **`cap`** элементов, не под `len`, и всегда обнуляется. Возвращается только указатель: `len`/`cap` компилятор кладёт в заголовок сам.

### `make([]T, n); copy(...)` → `makeslicecopy` — `slice.go:38`

Компилятор распознаёт связку «создать и сразу скопировать» и сводит её к одной функции: она выделяет память **без предварительного обнуления** той части, которую тут же перезапишет `memmove`, и обнуляет только хвост. Экономия — один проход по памяти.

### Слайс-выражение `a[low:high:max]`

Не аллоцирует ничего, просто собирает новый заголовок на тот же массив:

```
array = &a[low]
len   = high - low
cap   = max - low        // без третьего индекса: cap = cap(a) - low
```

Отсюда главное свойство: `cap` подсреза **тянется до конца исходного массива**, а не до конца подсреза.

### Стек или куча

Escape analysis решает, где будет backing array (`src/cmd/compile/internal/escape/utils.go`, `src/cmd/compile/internal/ir/cfg.go`):

| Случай | Где |
|---|---|
| `make([]T, K)`, K — константа, срез не убегает, `K*size ≤ 64 KB` | стек: компилятор объявляет `var arr [K]T` и берёт `arr[:K]` |
| `make([]T, n)`, n — переменная, срез не убегает | **гибрид**: `if cap <= K { var arr [K]T; s = arr[:len:cap] } else { s = makeslice(...) }`, где `K = 32/sizeof(T)` |
| срез убегает (возвращается, пишется в глобал, уходит в интерфейс) | куча |
| `K*size > 64 KB` (`MaxImplicitStackVarSize`) | куча |

Порог 32 байта — флаг компилятора `-d variablemakethreshold=N`. Проверить решение: `go build -gcflags=-m`.

## Append и рост

### Как компилятор разворачивает `s = append(s, e1, e2, e3)`

Из комментария в `src/cmd/compile/internal/ssagen/ssa.go:3686`:

```go
ptr, len, cap := s
len += 3
if uint(len) > uint(cap) {
    ptr, len, cap = growslice(ptr, len, cap, 3, typ)
}
*(ptr + (len-3)) = e1
*(ptr + (len-2)) = e2
*(ptr + (len-1)) = e3
s = slice{ptr, len, cap}
```

Быстрый путь — когда места хватает: рантайм не вызывается вообще, просто сдвигается `len` и пишутся элементы. Именно поэтому `append` в общий массив может перетереть чужие данные (см. [slices_guide.md](slices_guide.md)).

### `growslice` — `slice.go:177`

Вызывается **только** когда `newLen > oldCap`. Шаги:

```go
func growslice(oldPtr unsafe.Pointer, newLen, oldCap, num int, et *_type) slice {
    oldLen := newLen - num

    if et.Size_ == 0 {                    // []struct{} и подобное
        return slice{unsafe.Pointer(&zerobase), newLen, newLen}
    }

    newcap := nextslicecap(newLen, oldCap)          // 1. посчитать ёмкость

    capmem := roundupsize(newcap*et.Size_, noscan)  // 2. округлить до size class
    newcap = capmem / et.Size_                      //    cap может стать БОЛЬШЕ запрошенного

    if !et.Pointers() {
        p = mallocgc(capmem, nil, false)            // 3a. без обнуления...
        memclrNoHeapPointers(add(p, newlenmem), capmem-newlenmem) // ...кроме хвоста [newLen, cap)
    } else {
        p = mallocgc(capmem, et, true)              // 3b. с обнулением: GC не должен
        bulkBarrierPreWriteSrcOnly(...)             //     видеть мусор вместо указателей
    }

    memmove(p, oldPtr, oldLen*et.Size_)             // 4. перенести старые элементы
    return slice{p, newLen, newcap}                 // 5. новый заголовок
}
```

Кто что обнуляет — это важно для понимания, откуда берётся мусор за `len`:

| Диапазон | Кто заполняет |
|---|---|
| `[0, oldLen)` | `memmove` — копия старых элементов |
| `[oldLen, newLen)` | сам `append` после возврата из `growslice` |
| `[newLen, newCap)` | `growslice` обнуляет |

То есть **после роста** хвост за `len` гарантированно нулевой. А если рост не случился, в хвосте лежат старые данные этого же массива — это наблюдаемо (`s[:cap(s)]`).

Специализация по размеру элемента (`et.Size_ == 1`, `== PtrSize`, степень двойки, общий случай) нужна, чтобы заменить деление и умножение на сдвиги.

### `nextslicecap` — `slice.go:289`

```go
func nextslicecap(newLen, oldCap int) int {
    newcap := oldCap
    doublecap := newcap + newcap
    if newLen > doublecap {
        return newLen              // просят сразу больше, чем удвоение → даём ровно столько
    }
    const threshold = 256
    if oldCap < threshold {
        return doublecap           // маленькие срезы: ×2
    }
    for {
        newcap += (newcap + 3*threshold) >> 2   // плавный переход к ×1.25
        if uint(newcap) >= uint(newLen) { break }
    }
    if newcap <= 0 { return newLen }            // переполнение
    return newcap
}
```

| Условие | Новая ёмкость |
|---|---|
| `newLen > 2*oldCap` | ровно `newLen` |
| `oldCap < 256` | `2*oldCap` |
| `oldCap >= 256` | `oldCap + (oldCap + 768)/4` — коэффициент плавно падает с 1.75 к 1.25 |

Смысл: маленькие срезы удваиваются, чтобы амортизировать частые `append`; большие растут на ~25%, чтобы не удваивать мегабайты.

### `roundupsize` и size classes

Результат `nextslicecap` — это ещё не финальный `cap`. Он переводится в байты и округляется вверх до размера, которым оперирует аллокатор (`src/runtime/msize.go:16`, таблица `src/internal/runtime/gc/sizeclasses.go`: 8, 16, 24, 32, 48, 64, 80, 96, 112, 128, 144, …, 32768; свыше 32 КБ — округление до страницы). Затем байты делятся обратно на размер элемента.

Дополнительный нюанс: если элементы **содержат указатели** и выделяемый блок больше 512 байт (`gc.MinSizeForMallocHeader`), `mallocgc` кладёт перед объектом 8-байтовый заголовок для GC, и `roundupsize` это учитывает — восемь байт съедаются из блока. Отсюда «кривые» ёмкости.

Реально измеренные последовательности `cap` при `append` по одному элементу (срез убегает в кучу):

```
[]byte          : 8 16 32 64 128 256 512 896 1408 2048 3072 4096 5376 6912 9472
[]int           : 1 2 4 8 16 32 64 128 256 512  848 1280 1792 2560 3408 5120 7168
[]struct{24B}   : 1 2 4 8 16 32 64 128 256 512  853 1365 2048 3072 4096 5461 7168
[]*int          : 1 2 4 8 16 32 64 143 287 607 1023 1535 2303 3071 4095 6144 8192
[]string (16B)  : 1 2 4 8 16 32 71 143 303 591 1023 1535 2560 3584 5120 6656 8704
```

Разбор одной «кривой» строчки: у `[]*int` после 64 идёт не 128, а 143. `nextslicecap` вернул 128, это 1024 байта; тип содержит указатели и не влезает в лимит `MinSizeForMallocHeader = 512`, поэтому `roundupsize` прибавляет 8 байт заголовка (1032), округляет до класса 1152, вычитает заголовок обратно — 1144 байта, то есть 143 элемента.

В остальном видно всё сразу: удвоение до 256 элементов, дальше ~×1.25, повсюду подгонка под size class.

**Вывод для кода:** `cap` после `append` — величина, которую задаёт аллокатор, а не арифметика. Не завязывайся на её точное значение.

### Стековый буфер для первого append — `ssa.go:3776`

Отдельная оптимизация, из-за которой измерения могут выглядеть странно:

```go
// if l <= K {
//   if !used {
//     if oldLen == 0 {
//       var store [K]T    // массив на стеке
//       s = store[:l:K]
//       used = true
//     }
//   }
// }
// ... иначе обычный growslice ...
```

Условия: результат `append` не убегает, `sizeof(T) ≤ 32`, `K = 32/sizeof(T)`, срез до этого был **пустым** (`oldLen == 0`), и такое делается один раз на каждую переменную-приёмник. Отключается `-gcflags=-N`.

Наблюдаемый эффект: у не убегающего среза первый `append` сразу даёт `cap = 32/sizeof(T)` и **ноль аллокаций**, а у убегающего — `cap = 1`:

```
не убегает: [4 4 4 4 8 8]   // []int
убегает   : [1 2 4 4 8 8]
```

### `append(s, s2...)` и `append(s, str...)`

Разворачивается в `walkAppendArgs` (`src/cmd/compile/internal/walk/assign.go:465`): один вызов `growslice` на весь довесок плюс `memmove` (или `typedslicecopy`, если элементы содержат указатели и нужен write barrier). Поэлементного цикла нет.

## `copy` — `slice.go:355`

`copy(dst, src)` компилятор сводит к:

```go
n := len(dst); if n > len(src) { n = len(src) }
if dst.ptr != src.ptr { memmove(dst.ptr, src.ptr, n*sizeof(T)) }
```

- возвращает **минимум** из двух длин, ничего не аллоцирует и не растит `dst`;
- `memmove` корректно работает при **перекрытии** — сдвиг влево и вправо по одному массиву безопасен;
- `copy([]byte, string)` — отдельный разрешённый случай;
- для элементов с указателями вызывается `typedslicecopy` (с write barrier), иначе — чистый `memmove`.

## Элементы нулевого размера

`[]struct{}`, `[]([0]int)` и т.п. не занимают памяти. `growslice` возвращает указатель на глобальную переменную `zerobase` — один адрес на всю программу:

```go
z := make([]struct{}, 0)
z = append(z, struct{}{}, struct{}{})
// len=2, cap=2, unsafe.SliceData(z) == адрес zerobase у любого такого среза
```

Счётчик `len` при этом настоящий — на таких срезах можно считать, но не хранить.

## GC и срезы

Сборщик сканирует **объект целиком**, а не диапазон `[0, len)`. Указатели, оставшиеся за `len`, но внутри `cap`, — живые корни:

```go
s := make([]*big, 3)   // три объекта
s = s[:1]              // "удалили" два
runtime.GC()           // освобождено: 0 из 2

s = s[:3]; clear(s[1:]); s = s[:1]
runtime.GC()           // освобождено: 2 из 2
```

(Проверено финализаторами.) Практическое следствие в [slices_guide.md](slices_guide.md), раздел про утечки.

Второй эффект того же свойства: подсрез держит живым **весь** backing array, включая ту часть, на которую никто не смотрит.

## Паники: что и когда

| Выражение | Сообщение |
|---|---|
| `s[5]`, `len(s)==3` | `index out of range [5] with length 3` |
| `s[1:5]`, `cap(s)==3` | `slice bounds out of range [:5] with capacity 3` |
| `s[3:1]` | `slice bounds out of range [3:1]` |
| `s[:2:5]`, `cap(s)==3` | `slice bounds out of range [::5] with capacity 3` |
| `make([]int, n)`, `n<0` или слишком велик | `makeslice: len out of range` |
| `make([]int, 5, 2)` | `makeslice: cap out of range` |
| `var s []int; _ = s[0]` | `index out of range [0] with length 0` |
| `var s []int; _ = s[0:0]` | паники нет — это валидное выражение |

Индексация проверяется границей `len`, слайсинг — границей `cap`. Константные нарушения (`make([]int, -1)` с литералом) ловятся ещё компилятором.

## Шпаргалка

```
slice = { array *T, len int, cap int }   ← 24 байта, копируется по значению

s = append(s, x):
  ├─ len+1 <= cap? → пишем на месте, рантайм не вызывается
  │                  (общий backing array → можно задеть соседей)
  └─ иначе growslice:
        newcap = nextslicecap:
            newLen > 2*cap → newLen
            cap < 256      → cap*2
            cap >= 256     → cap + (cap+768)/4
        → roundupsize (size class, -8 байт для типов с указателями)
        → mallocgc → memmove старых элементов → обнуление [newLen, cap)
        → НОВЫЙ заголовок (обязательно присвоить обратно)
```

| Операция | Стоимость |
|---|---|
| копия переменной-среза | O(1), 24 байта |
| `s[i]` | O(1) + проверка границы |
| `s[a:b]` | O(1), только новый заголовок |
| `append` без роста | O(1) |
| `append` с ростом | O(n): аллокация + `memmove` |
| `copy` | O(min(len)), один `memmove` |
| `clear(s)` | O(len), `memclr` |
| амортизированная стоимость n append'ов | O(n) |
