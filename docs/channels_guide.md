# Каналы в Go: всё, что нужно знать на практике

Поведение проверено запуском на Go 1.26.1. Внутреннее устройство — `hchan`, `sudog`, `selectgo` — в [Channel.md](Channel.md).

## 1. Создание

```go
ch := make(chan int)        // небуферизованный
ch := make(chan int, 10)    // буфер на 10
var ch chan int             // nil — никогда не готов
done := make(chan struct{}) // сигнальный канал, элемент занимает 0 байт
```

Направление — часть типа, и это лучший способ зафиксировать роль в сигнатуре:

```go
func produce(out chan<- int)   // только отправка
func consume(in <-chan int)    // только приём
```

Двунаправленный канал приводится к направленному автоматически, обратно — нет. `close` на `<-chan` запрещён компилятором: закрывать может только тот, кто отправляет.

## 2. Три состояния канала

| Операция | nil | открыт | закрыт |
|---|---|---|---|
| `ch <- x` | блок навсегда | отправляет или блокирует | **panic** |
| `<-ch` | блок навсегда | принимает или блокирует | ноль, `ok == false` (буфер сперва дочитывается) |
| `close(ch)` | **panic** | закрывает | **panic** |
| `len`/`cap` | 0 | текущее / ёмкость | как обычно |
| `for range ch` | блок навсегда | идёт, пока не закроют | завершается |

Асимметрия закрытого канала — «читать можно, писать нельзя» — и есть причина главного правила.

## 3. Кто закрывает

**Закрывает только отправитель, и только если он один.** Получатель закрывать не должен: у него нет способа узнать, не пишет ли кто-то прямо сейчас, а запись в закрытый канал — паника, которую нельзя предотвратить проверкой (`if !closed { ch <- x }` — гонка по определению).

Если отправителей несколько:

```go
var wg sync.WaitGroup
for _, w := range workers {
    wg.Go(func() { out <- work(w) })   // wg.Go — Go 1.25; раньше wg.Add(1) + go func(){ defer wg.Done() }
}
go func() { wg.Wait(); close(out) }()  // закрывает тот, кто дождался всех
```

Если нужно остановить отправителей — это делается **другим** каналом, а не закрытием того, в который пишут:

```go
select {
case out <- v:
case <-done:      // сигнал «прекращай»
    return
}
```

Закрывать канал ради освобождения памяти не нужно: недостижимый канал соберёт GC.

## 4. Закрытие как широковещательный сигнал

Закрытие будит **всех** ждущих получателей сразу, и каждый последующий приём тоже завершается мгновенно. Это единственный примитив в Go с семантикой broadcast:

```go
done := make(chan struct{})
// ... в четырёх горутинах: <-done
close(done)   // проснулись все четыре
```

Проверено: четыре ждущие горутины, один `close`, все четыре проснулись. Отсюда идиома `done`/`quit`-канала — и `context.Context.Done()` устроен ровно так же.

Закрытие можно проверять неблокирующе:

```go
select {
case <-done: return  // уже закрыт
default:             // ещё нет
}
```

## 5. Небуферизованный или буферизованный

**Небуферизованный — это рандеву.** Отправитель не продолжит работу, пока получатель не заберёт значение. Наблюдаемый порядок:

```
отправитель до → получатель до → отправитель после
```

Строка «отправитель после» не может выполниться раньше, чем получатель дошёл до `<-ch`. Это даёт синхронизацию, а не только передачу данных.

**Буферизованный — это очередь.** Отправитель продолжает работу, пока есть место. Гарантии слабее: факт успешной отправки не означает, что кто-то это прочитал.

Как выбирать размер буфера:

| Размер | Когда |
|---|---|
| 0 | нужна синхронизация; нужно знать, что значение принято |
| 1 | сигнал «есть событие», который не должен теряться и не должен блокировать отправителя (`select { case ch <- struct{}{}: default: }`) |
| N = число воркеров / размер батча | сглаживание рывков производителя, разъединение скоростей |
| большой «на всякий случай» | почти всегда ошибка: прячет проблему скорости, увеличивает задержку между событием и реакцией, растит потребление памяти |

Буфер не ускоряет обработку — он только позволяет производителю убежать вперёд на N элементов.

## 6. Гарантии памяти

Каналы — не только передача значений, но и точки синхронизации. Из модели памяти Go:

- отправка **происходит раньше**, чем завершается соответствующий приём;
- закрытие происходит раньше, чем приём, вернувший нулевое значение из-за закрытия;
- приём из небуферизованного канала происходит раньше, чем завершается соответствующая отправка;
- k-й приём из канала ёмкости C происходит раньше, чем завершается (k+C)-я отправка.

Практический вывод: всё, что горутина записала **до** отправки в канал, видно получателю **после** приёма. Поэтому передавать через канал указатель или структуру безопасно без дополнительных мьютексов — при условии, что отправитель больше к этим данным не притрагивается.

```go
data := compute()
ch <- data        // получатель увидит compute() полностью завершённой
// здесь data трогать уже нельзя: владение передано
```

Канал передаёт **владение**, а не даёт совместный доступ. Значение при отправке копируется; если внутри указатель или срез — копируется указатель, и данные остаются общими.

## 7. `range` по каналу

```go
for v := range ch { ... }   // завершится ТОЛЬКО после close(ch)
```

- Без `close` цикл повиснет — а если работают другие горутины, дедлок не обнаружится и программа просто зависнет.
- `break` или `return` из цикла оставляет отправителя заблокированным навсегда. Проверено: `break` из `range` по небуферизованному каналу оставил горутину-производителя висеть. Если выход возможен — нужен `select` с `done`-каналом на стороне отправителя.
- `v, ok := <-ch` в цикле `range` не нужен: закрытие завершает цикл, нулевые значения не выдаются.

## 8. `select`

```go
select {
case v := <-a:        // приём
case b <- x:          // отправка
case <-ctx.Done():    // отмена
default:              // если ничего не готово прямо сейчас
}
```

- **Готовых веток несколько — выбирается случайная.** Измерено на 30 000 итераций с тремя готовыми ветками: 10063 / 10151 / 9786. Приоритетов нет и добиться их нельзя — только вложенным `select`:
  ```go
  select {
  case <-urgent:        // сначала проверяем срочное
  default:
      select {
      case <-urgent:
      case <-normal:
      }
  }
  ```
- **`default` делает операцию неблокирующей.** Компилятор превращает такой `select` в один вызов `selectnbsend`/`selectnbrecv` — это дёшево.
- **`default` в цикле без паузы — активное ожидание**, которое сжигает ядро. Почти всегда это ошибка.
- **nil-канал выключает ветку.** Классический приём для пайплайна, где один из входов закончился:
  ```go
  for a != nil || b != nil {
      select {
      case v, ok := <-a:
          if !ok { a = nil; continue }   // больше эту ветку не рассматриваем
          use(v)
      case v, ok := <-b:
          if !ok { b = nil; continue }
          use(v)
      }
  }
  ```
- **`select {}` без веток** — вечный сон текущей горутины. В `main` это `deadlock`, если других горутин нет.
- Закрытый канал в `select` **всегда готов**. Ветка `case <-done:` будет срабатывать бесконечно, поэтому после неё обычно `return`.
- Цена: `select` из двух веток — 43 нс против 18 нс у прямой операции. На каждую ветку создаётся `sudog` и делается постановка в очередь. Для горячего цикла на два-три канала это нормально; для `select` на десяток каналов в цикле — уже стоит подумать.

## 9. Таймауты и таймеры

```go
select {
case v := <-ch:
case <-time.After(time.Second):
    return errors.New("таймаут")
}
```

С Go 1.23 неостановленные таймеры собираются сборщиком мусора, так что `time.After` в цикле больше не удерживает память до срабатывания. Проверено: 200 000 брошенных `time.After(time.Hour)` дали прирост кучи 24 КБ. На Go ≤ 1.22 это была известная утечка, и там требовалось:

```go
t := time.NewTimer(time.Second)
defer t.Stop()
select {
case v := <-ch:
case <-t.C:
}
```

`time.Ticker` **нужно останавливать всегда**, независимо от версии — он не одноразовый:

```go
tk := time.NewTicker(time.Second)
defer tk.Stop()
for range tk.C { ... }
```

У каналов таймеров `len` и `cap` всегда показывают 0, хотя внутри реализация буферизованная.

В реальном коде вместо самодельных таймаутов обычно нужен `context`:

```go
ctx, cancel := context.WithTimeout(ctx, time.Second)
defer cancel()
select {
case v := <-ch:
case <-ctx.Done():
    return ctx.Err()
}
```

`ctx.Done()` — тот же закрываемый канал, только отмена распространяется по всему дереву вызовов.

## 10. Утечки горутин

Заблокированная навсегда горутина не собирается сборщиком мусора и держит всё, на что ссылается. Дедлок при этом **не** диагностируется: рантайм ругается, только если спят абсолютно все горутины.

Четыре типовых сценария:

```go
// 1. Отправка, которую никто не прочитает
go func() { ch <- result }()    // получатель ушёл по таймауту → горутина висит вечно
// лечение: буфер на 1, либо select с ctx.Done()

// 2. Приём из канала, в который никто не напишет
go func() { <-ch }()            // отправитель умер по ошибке
// лечение: close по defer на стороне отправителя

// 3. range без close
for v := range ch { ... }       // отправитель забыл close

// 4. Выход из потребителя раньше времени
for v := range ch { if bad(v) { return } }   // производитель остался в блоке
```

Как ловить:

- `runtime.NumGoroutine()` до и после — в тестах;
- `go.uber.org/goleak` в `TestMain`;
- `curl localhost:6060/debug/pprof/goroutine?debug=1` — постоянно растущий стек в одном месте;
- `SIGQUIT` по процессу печатает все стеки с причинами (`[chan receive]`, `[chan send]`, `[select]`).

**Правило:** у каждой запущенной горутины должен быть ясный ответ на вопрос «при каких условиях она завершится». Если ответ содержит «если получатель не уйдёт раньше» — это утечка.

## 11. Паттерны

**Пул воркеров.**

```go
jobs := make(chan Job)
results := make(chan Result, len(list))

var wg sync.WaitGroup
for range runtime.NumCPU() {
    wg.Go(func() { for j := range jobs { results <- process(j) } })
}
for _, j := range list { jobs <- j }
close(jobs)               // воркеры выйдут из range
wg.Wait()
close(results)
```

**Fan-in (слияние).**

```go
func merge[T any](chans ...<-chan T) <-chan T {
    out := make(chan T)
    var wg sync.WaitGroup
    for _, c := range chans {
        wg.Go(func() { for v := range c { out <- v } })
    }
    go func() { wg.Wait(); close(out) }()
    return out
}
```

**Семафор (ограничение параллелизма).**

```go
sem := make(chan struct{}, 10)     // не больше 10 одновременно
for _, task := range tasks {
    sem <- struct{}{}
    go func() { defer func() { <-sem }(); run(task) }()
}
```

**Сигнал без потери и без блокировки** (буфер на 1 как «флаг»):

```go
notify := make(chan struct{}, 1)
select {
case notify <- struct{}{}:   // взвели флаг
default:                     // он уже взведён — второй раз не надо
}
```

**Результат с ошибкой.**

```go
type res struct { v Value; err error }
ch := make(chan res, 1)          // буфер 1, чтобы горутина не зависла при таймауте
go func() { v, err := call(); ch <- res{v, err} }()
select {
case r := <-ch: return r.v, r.err
case <-ctx.Done(): return zero, ctx.Err()
}
```

**Пайплайн с отменой.** Каждая стадия принимает `<-chan` и `ctx`, возвращает `<-chan`, закрывает свой выход по `defer` и проверяет `ctx.Done()` на каждой отправке.

**`errgroup`** (`golang.org/x/sync/errgroup`) закрывает большинство этих случаев без ручных каналов: ограничение параллелизма, первая ошибка, общий контекст.

## 12. Когда канал не нужен

| Задача | Инструмент |
|---|---|
| защитить общее состояние | `sync.Mutex` / `sync.RWMutex` — в 7–40 раз быстрее канала |
| счётчик, флаг | `sync/atomic` |
| дождаться N горутин | `sync.WaitGroup` (с 1.25 — `wg.Go`) |
| выполнить ровно один раз | `sync.Once` |
| кэш с редкими записями | `sync.Map` или мьютекс + обычная карта |
| передача владения, конвейер, уведомление, отмена | канал |

Формулировка «не общайтесь через общую память — делите память через общение» не означает, что мьютексов надо избегать. Она про то, что владение данными должно переходить явно.

## 13. Тестирование конкурентного кода

- `go test -race` — обязательно в CI. Детектор гонок ловит именно то, что не ловится глазами.
- `testing/synctest` (стабилен с Go 1.25) — виртуальное время и детерминированное ожидание:
  ```go
  func TestTimeout(t *testing.T) {
      synctest.Test(t, func(t *testing.T) {
          // time.Sleep(time.Hour) внутри выполняется мгновенно
          // synctest.Wait() ждёт, пока все горутины «пузыря» заблокируются
      })
  }
  ```
  Проверено: тест с часовыми задержками проходит за 0.00 с. Это убирает `time.Sleep` из тестов и делает их стабильными.
- `-cpu 1,4` — прогон на разном числе процессоров вскрывает зависимость от планировщика.

## 14. Шпаргалка ошибок

| Симптом | Причина |
|---|---|
| `panic: send on closed channel` | закрывает не тот, кто отправляет, или отправителей несколько |
| `panic: close of closed channel` | двойное закрытие; нужен `sync.Once` или один владелец |
| `panic: close of nil channel` | канал не создан через `make` |
| `fatal error: all goroutines are asleep - deadlock!` | все горутины заблокированы; частый случай — отправка в небуферизованный канал без читателя в той же горутине |
| Программа висит, но ошибки нет | часть горутин утекла, а другие ещё работают — детектор дедлока молчит |
| `range` по каналу не завершается | никто не вызвал `close` |
| Число горутин растёт | отправка в канал, который перестали читать (обычно после таймаута) |
| Значения теряются | несколько получателей на одном канале — каждое значение достаётся ровно одному |
| Получатель видит устаревшие данные | отправитель продолжил менять то, на что отдал указатель |
| `select` игнорирует «важный» канал | приоритетов нет, выбор случайный |
| 100% CPU | `select` с `default` в цикле без паузы |
| Ветка `case <-done` срабатывает бесконечно | закрытый канал всегда готов — после неё нужен `return` |
| Тест иногда падает | `time.Sleep` вместо синхронизации; нужен `synctest` или явное ожидание |
