## 1. ОСНОВЫ GC В GO

### 1.1. Тип сборщика и почему именно такой

🏛️ **[ДИЗАЙН]** Сборщик мусора в Go — это:

| Свойство | Значение | Что это значит |
|---|---|---|
| **Concurrent** (параллельный) | да | Работает одновременно с вашей программой, почти не останавливая её |
| **Tri-color mark-and-sweep** | да | Трёхцветная маркировка + выметание |
| **Non-generational** | да (не поколенческий) | Нет разделения на «молодые» и «старые» объекты |
| **Non-compacting** | да (не сжимающий/не перемещающий) | Объекты никогда не двигаются в памяти после аллокации |
| **Non-moving** | да | Указатель на объект остаётся валидным всю жизнь объекта |

Разберём каждое решение и **почему** оно выбрано.

#### Mark-and-sweep (маркировка и выметание)

Базовый принцип трассирующего (tracing) сборщика:
1. **Mark (маркировка):** начиная от *корней* (roots) — глобальные переменные, стеки горутин, регистры — обойти весь граф достижимых объектов и пометить их как «живые».
2. **Sweep (выметание):** всё, что не помечено, — мусор; его память возвращается в пулы для повторного использования.

**Ключевая идея:** сборщик не ищет мусор напрямую. Он находит *живое*, а мусором объявляется всё остальное («по остаточному принципу»). Это фундаментально отличается от подсчёта ссылок (см. Python в разделе 4).

#### Почему concurrent (конкурентный)?

🏛️ Главная цель дизайна Go GC — **низкая задержка (low latency)**, а не максимальная пропускная способность (throughput). Go создавался в Google для сетевых сервисов, где важнее всего, чтобы 99-й перцентиль времени ответа был предсказуемо мал. «Мир замер на 100 мс» для веб-сервиса — катастрофа.

Поэтому основную работу — маркировку — сборщик выполняет **параллельно** с работающей программой. Программа в терминологии GC называется **mutator** (мутатор — потому что она *мутирует*, изменяет граф объектов), а сборщик — **collector**.

#### Почему НЕ поколенческий (non-generational)?

Это самое частое «удивление» у людей с опытом JVM/.NET.

**Гипотеза о поколениях (generational hypothesis):** «большинство объектов умирают молодыми». Поколенческие сборщики эксплуатируют это: часто и дёшево собирают «молодое поколение», редко — «старое».

Почему Go пошёл иначе:

1. 🏛️ **Escape analysis снимает большую часть нагрузки.** Компилятор Go размещает недолговечные объекты **на стеке**, а не в куче (см. §1.6). Стековые объекты вообще не касаются GC — они освобождаются мгновенно при возврате из функции. То есть «умирающие молодыми» объекты в Go во многих случаях *до кучи не доходят*. Это уменьшает главный выигрыш поколенческого подхода.

2. 🏛️ **Поколенческий GC почти всегда требует перемещения объектов** (промоушен из young в old-поколение) и **write barrier на запись в старые объекты** (для отслеживания old→young ссылок). Перемещение объектов противоречит модели Go, где активно используются внутренние указатели (`&s.field`), interop с C (cgo), и указатели передаются повсюду.

3. 🔧 **Инженерный прагматизм.** Команда Go неоднократно (Rick Hudson, Austin Clements) заявляла: поколенческий GC — на столе, но текущий подход даёт достаточно низкую задержку, а сложность поколенческого сборщика с write-barrier’ами высока. Вместо этого силы вложены в конкурентность и в escape analysis.

#### Почему НЕ сжимающий / не перемещающий (non-compacting / non-moving)?

**Compaction** — это дефрагментация кучи: живые объекты сдвигаются вплотную, освобождая непрерывные области. Плюс — устраняется фрагментация; минус — надо обновить все указатели на перемещённые объекты, что сложно и требует пауз или сложных барьеров чтения (read barriers, как в ZGC).

Go выбрал не перемещать, потому что:
- 🏛️ **Внутренние указатели.** В Go легально взять адрес поля структуры или элемента массива (`&arr[3]`). Если объект переместить, такой указатель надо уметь найти и обновить — крайне дорого.
- 🏛️ **Стабильные адреса упрощают cgo и unsafe.** Указатель, переданный в C-код, не должен «уехать».
- 🏛️ **Проблему фрагментации решает size-class аллокатор** (см. §1.5), заимствованный из TCMalloc. Объекты одинакового размера кладутся в одни и те же спаны, поэтому «дыр» произвольного размера почти не образуется.

> 🔧 **[РЕАЛИЗАЦИЯ, Go 1.25+]** 📌 В Go 1.25 появился и в **Go 1.26 включён по умолчанию** новый маркер **Green Tea GC** (см. §3). Он меняет *как* сканируется память (по спанам, а не по отдельным объектам), но НЕ меняет фундаментальный дизайн: сборщик по-прежнему concurrent, non-moving, non-generational, tri-color. Проверено в исходниках: `src/internal/buildcfg/exp.go` → `GreenTeaGC: true` в baseline.

### 1.2. Трёхцветная маркировка (tri-color marking)

🏛️ **[ДИЗАЙН]** Абстракция Дейкстры для конкурентной маркировки. Каждый объект в куче в любой момент имеет один из трёх «цветов»:

- ⚪ **Белый (white):** ещё не обработан. В конце цикла все оставшиеся белые объекты — мусор.
- ⚫ **Серый (grey):** объект жив (достижим), но его *поля ещё не просканированы* — мы ещё не прошли по указателям внутри него.
- ⬛ **Чёрный (black):** объект жив И все его исходящие указатели уже обработаны. Чёрный объект больше не пересматривается.

> ⚠️ В реальном рантайме Go «цвета» не хранятся как поле у объекта. 🔧 Серое множество — это **рабочие очереди (work queues / gcWork)**; чёрный/белый различается битами в **mark bitmap** спана. «Цвет» — это удобная ментальная модель, а не байт в объекте.

#### Алгоритм (псевдокод)

```
// Инициализация
все объекты = БЕЛЫЕ
корни (стеки, глобалы) → красим достижимое в СЕРЫЙ, кладём в очередь

// Основной цикл маркировки
while очередь_серых не пуста:
    obj = взять_серый()
    for ptr in исходящие_указатели(obj):
        target = разыменовать(ptr)
        if target БЕЛЫЙ:
            target = СЕРЫЙ          // нашли нового живого
            положить_в_очередь(target)
    obj = ЧЁРНЫЙ                     // все поля обработаны

// Завершение
всё, что осталось БЕЛЫМ → мусор → sweep
```

**Аналогия.** Представьте, что вы красите комнаты особняка фонариком. Серые — комнаты, куда вы уже вошли, но ещё не проверили все двери. Чёрные — комнаты, где вы проверили каждую дверь. Белые — куда вы ещё не заглядывали. Когда серых не осталось, все непосещённые (белые) комнаты можно снести.

#### Инвариант трёхцветной маркировки

🏛️ Корректность держится на **сильном трёхцветном инварианте**:

> **Ни один чёрный объект не должен ссылаться напрямую на белый объект.**

Пока это выполняется, любой белый объект гарантированно недостижим от «завершённых» (чёрных) — и его можно собрать.

### 1.3. Проблема конкурентности и write barrier

Вот здесь начинается самое интересное. Пока сборщик красит объекты, **мутатор продолжает менять указатели**. Это может нарушить инвариант.

#### Классический сценарий гонки («потерянный объект»)

Пусть:
- Объект `A` уже стал **чёрным** (просканирован).
- Объект `C` пока **белый** (сборщик до него не дошёл), но достижим только через `B`.

Мутатор выполняет:
```go
A.ptr = C      // (1) чёрный A теперь ссылается на белый C
B.ptr = nil    // (2) единственная старая ссылка на C уничтожена
```

Теперь:
- `A` чёрный → сборщик его больше **не пересмотрит** → он не увидит новую ссылку на `C`.
- `B` больше не ссылается на `C`.
- `C` остаётся **белым** → будет ошибочно собран как мусор, хотя он жив! 💥 **Use-after-free.**

Инвариант нарушен: чёрный `A` ссылается на белый `C`.

#### Write barrier — решение

🏛️ **[ДИЗАЙН]** **Write barrier (барьер записи)** — это небольшой фрагмент кода, который компилятор **автоматически вставляет перед каждой записью указателя в кучу**, пока GC активен. Барьер «сообщает» сборщику о том, что граф изменился, и подкрашивает нужные объекты, восстанавливая инвариант.

Существует два классических вида:
- **Барьер вставки Дейкстры (Dijkstra insertion barrier):** при записи `slot = ptr` красит **новый** объект (`ptr`) в серый. «Если чёрный начал ссылаться на белого — сделаем белого серым».
- **Барьер удаления Юасы (Yuasa deletion barrier):** при записи красит в серый **старый** объект, ссылка на который перезаписывается. «Прежде чем разорвать ссылку — подстрахуемся и сохраним старую цель».

#### 📌 Гибридный барьер Go (hybrid write barrier)

🔧 **[РЕАЛИЗАЦИЯ, с Go 1.8]** Go использует **гибридный барьер** = Yuasa (удаление) + Dijkstra (вставка). Проверено в `src/runtime/mbarrier.go`:

> «Go uses a hybrid barrier that combines a Yuasa-style deletion barrier — which shades the object whose reference is being overwritten — with Dijkstra insertion barrier — which shades the object whose reference is being written.»

Псевдокод барьера (концептуально):
```go
// перед выполнением: *slot = ptr
writePointer(slot, ptr):
    shade(*slot)        // Yuasa: подкрасить СТАРОЕ значение (что перезаписываем)
    if текущая_горутина_серая:
        shade(ptr)      // Dijkstra: подкрасить НОВОЕ значение
    *slot = ptr
```

🏛️ **Зачем именно гибрид — ключевой выигрыш:** он позволяет **не пересканировать стеки повторно (no stack re-scanning)**. Стек горутины сканируется один раз, помечается чёрным и больше не требует STW-перекраски. Именно это устранило самые долгие паузы (см. §3, Go 1.8). До гибридного барьера завершающая фаза требовала повторного STW-сканирования стеков, что и было главным источником длинных пауз.

> 🔧 Барьер активен **только во время фазы маркировки**. Когда GC не работает, запись указателя — это просто запись, без накладных расходов. Компилятор вставляет проверку глобального флага `writeBarrier.enabled`.

**Стоимость.** Write barrier — это не бесплатно: каждая запись указателя в куче во время маркировки чуть дороже. Это осознанный размен: небольшой оверхед throughput ради радикально меньших пауз.

### 1.4. Mutator vs Collector: как они уживаются

🏛️ **[ДИЗАЙН]** Полный цикл GC в Go (упрощённо):

```
   [программа работает]
        │
        │ heap дорос до триггера (см. pacer, §2.4)
        ▼
 ┌─────────────────────┐
 │ 1. Sweep Termination│  ← STW (короткий): завершить выметание прошлого цикла
 └─────────────────────┘
        ▼
 ┌─────────────────────┐
 │ 2. Mark Setup / STW │  ← STW (короткий): включить write barrier,
 └─────────────────────┘     подготовить корни, перевести в concurrent mark
        ▼
 ┌─────────────────────┐
 │ 3. Concurrent Mark  │  ← ПАРАЛЛЕЛЬНО с программой (основная работа!)
 │    + Mark Assist    │     mutator помогает маркировать (assist)
 └─────────────────────┘
        ▼
 ┌─────────────────────┐
 │ 4. Mark Termination │  ← STW (короткий): финализация, выключить barrier
 └─────────────────────┘
        ▼
 ┌─────────────────────┐
 │ 5. Concurrent Sweep │  ← ПАРАЛЛЕЛЬНО: память выметается лениво,
 └─────────────────────┘     по мере запросов на аллокацию
```

#### Дозирование ресурсов CPU

🔧 **[РЕАЛИЗАЦИЯ]** Во время конкурентной маркировки Go старается отдавать сборщику **~25% CPU** (по умолчанию `GOMAXPROCS/4` выделенных worker-горутин). Остальное — программе.

#### Mark Assist — «плати по мере загрязнения»

🏛️ Есть тонкость: что если программа аллоцирует **быстрее**, чем сборщик успевает маркировать? Куча росла бы неограниченно, а цель по памяти была бы сорвана.

Решение — **mark assist (маркировка в кредит)**: если горутина аллоцирует память во время активного GC, она **обязана сама выполнить порцию маркировки** пропорционально объёму аллокации. Работает принцип «загрязнитель платит»: чем больше горутина мусорит, тем больше помогает убирать. Это создаёт естественную обратную связь — быстрый аллокатор притормаживается, и куча не «убегает» от сборщика.

```go
// Концептуально, при аллокации во время GC:
if gcBlackenEnabled {
    assistWork := bytesAllocated * assistRatio  // "долг" горутины
    gcAssistAlloc(assistWork)                    // отработать долг маркировкой
}
```

### 1.5. Выделение памяти: mcache → mcentral → mheap

🏛️ **[ДИЗАЙН]** Аллокатор Go — прямой наследник **TCMalloc** (Thread-Caching Malloc от Google). Он организован иерархически, чтобы минимизировать блокировки, и тесно связан с GC (маркировка/выметание работают по тем же спанам).

#### Ключевые структуры

**Span (спан)** — 🔧 непрерывный участок памяти, кратный **странице в 8 КБ** (`PageSize = 8192`, проверено в `src/internal/runtime/gc/malloc.go`). Спан нарезан на объекты **одного size class**. Именно спан — единица управления памятью и единица маркировки.

**Size classes (размерные классы)** — 🔧 📌 В Go 1.26 их около **68** (`src/internal/runtime/gc/sizeclasses.go`). Объекты «округляются» вверх до ближайшего класса:

```
// фрагмент таблицы из sizeclasses.go (Go 1.26.4):
// class  bytes/obj  bytes/span  objects  tail waste  max waste
//     1          8        8192     1024           0     87.50%
//     2         16        8192      512           0     43.75%
//     3         24        8192      341           8     29.24%
//     4         32        8192      256           0     21.88%
//     ...
//    максимальный small-объект: MaxSmallSize = 32768 (32 КБ)
```

Например, запрос на 17 байт → попадает в класс 24 байта (7 байт «tail waste» — плата за отсутствие фрагментации). Это и есть механизм борьбы с фрагментацией без compaction: все дыры имеют фиксированные размеры и мгновенно переиспользуются.

**Три уровня кэширования:**

| Уровень | Что это | Блокировки | Аналогия |
|---|---|---|---|
| **mcache** | Кэш спанов на каждый **P** (логический процессор) | 🏛️ **Без блокировок!** | Личный ящик инструментов на рабочем столе |
| **mcentral** | Центральный список спанов **на каждый size class** | Мьютекс на класс | Общий склад инструментов по типам |
| **mheap** | Вся куча целиком; общается с ОС | Глобальный мьютекс | Поставка со склада поставщика (ОС) |

**Путь аллокации маленького объекта (fast path):**
```
p.mcache имеет свободный слот нужного size class?
  ├─ да  → отдать слот (БЕЗ блокировок, супербыстро) ✅
  └─ нет → взять новый спан из mcentral[class] (мьютекс класса)
             └─ mcentral пуст → mheap выделяет спан (глоб. мьютекс)
                                   └─ mheap пуст → запросить память у ОС (mmap)
```

#### Три категории объектов по размеру

🔧 **[РЕАЛИЗАЦИЯ]**
1. **Tiny (< 16 байт, `TinySize = 16`), без указателей** — например, маленькие строки, `[4]byte`. Несколько таких объектов **упаковываются в один 16-байтовый блок** (tiny allocator). Резко снижает расход на мелочь.
2. **Small (16 байт … 32 КБ)** — основной путь, через size classes и mcache.
3. **Large (> 32 КБ)** — выделяются напрямую из mheap отдельными спанами, минуя mcache.

#### Связь с GC

🏛️ Аллокатор и сборщик используют **одни и те же спаны**:
- У каждого спана есть **allocation bitmap** (какие слоты заняты) и **mark bitmap** (какие слоты живые).
- **Sweep** — это, по сути, `alloc_bits = mark_bits`: освобождаются слоты, что не были помечены. Делается **лениво** — спан выметается в момент, когда из него в следующий раз просят аллокацию (или фоновым sweeper’ом).
- Информация о том, **где внутри объекта лежат указатели**, хранится отдельно (тип/`GCProgram`), чтобы маркировщик знал, по каким смещениям ходить.

### 1.6. Escape analysis: стек или куча?

🏛️ **[ДИЗАЙН, но конкретные решения — деталь компилятора]** **Escape analysis (анализ убегания)** — статический анализ компилятора, решающий: может ли объект жить только в пределах кадра стека функции, или он «убегает» (escapes) за его границы и обязан лежать в куче.

**Правило (упрощённо):** если компилятор может *доказать*, что после возврата из функции на объект не останется ни одной ссылки, — объект размещается **на стеке**. Стековая память освобождается мгновенно (сдвигом указателя стека) и **никогда не нагружает GC**. Это — важнейшая оптимизация, снимающая с GC огромную долю работы.

**Что заставляет объект «убегать» в кучу:**
- Возврат указателя на локальную переменную из функции.
- Сохранение указателя в структуру/слайс/мапу, живущую дольше функции.
- Передача в `interface{}` / `any` (часто, т.к. тип стирается).
- Захват переменной по ссылке в замыкании, которое переживает функцию.
- Слишком большой объект (не помещается в разумный стек) или размер, неизвестный на этапе компиляции.
- Вызов через интерфейс, где компилятор не видит конкретную реализацию.

#### Как посмотреть решения компилятора

```bash
go build -gcflags='-m' ./...
# или подробнее (два -m):
go build -gcflags='-m -m' ./...
```

Пример:
```go
package main

func doesNotEscape() int {
    x := 42          // останется на стеке
    return x         // возвращаем ЗНАЧЕНИЕ, не адрес
}

func escapes() *int {
    y := 42          // "y escapes to heap"
    return &y        // возвращаем АДРЕС локальной переменной
}
```

Вывод `go build -gcflags='-m'`:
```
./main.go: moved to heap: y      # escapes() — y уехал в кучу
                                 # doesNotEscape() — ничего, x на стеке
```

**Практический вывод:** возврат `&y` из функции в Go **безопасен** (в отличие от C, где это dangling pointer) — компилятор просто разместит `y` в куче. Но это стоит одной аллокации и нагрузки на GC. Иногда переписывание API с указателей на значения убирает аллокации целиком (см. §5).

### 1.7. Green Tea GC — span-ориентированная маркировка

📌 🔧 **[РЕАЛИЗАЦИЯ, Go 1.25 эксперимент → Go 1.26 по умолчанию]** Это самое свежее крупное изменение в GC. Разбор основан на исходниках этой копии: [`src/runtime/mgcmark_greenteagc.go`](src/runtime/mgcmark_greenteagc.go) (1280 строк, в шапке — фактический design-doc).

> ⚠️ **Это деталь реализации.** Меняется *как физически обходится память* на фазе mark. Фундаментальный дизайн (concurrent, tri-color, non-moving, non-generational) **не меняется**.

#### Сначала: что такое «спан» (span) — конкретно

🏛️ **Спан** — базовая единица управления памятью в куче. Физически это **непрерывный кусок памяти из одной или нескольких страниц по 8 КБ**, нарезанный на слоты **одного размерного класса** (см. §1.5). В коде — структура `mspan` ([`src/runtime/mheap.go:422`](src/runtime/mheap.go)):

```go
type mspan struct {
    startAddr uintptr // адрес первого байта спана
    npages    uintptr // сколько страниц по 8 КБ занимает
    nelems    uint16  // сколько слотов (объектов) в спане
    // ...
    // Объект n лежит по адресу: startAddr + n*elemsize
}
```

Пример спана для size class 32 байта (одна страница 8 КБ → 256 слотов):
```
┌──────┬──────┬──────┬──────┬─────┬────────┐
│ obj0 │ obj1 │ obj2 │ obj3 │ ... │ obj255 │
└──────┴──────┴──────┴──────┴─────┴────────┘
 base   +32    +64    +96          адреса — чистая арифметика
```

🏛️ **Ключевое свойство:** по адресу любого указателя `p` рантайм за O(1) вычисляет его спан и индекс слота — округлением адреса вниз до границы страницы. Прямо из кода Green Tea (`tryDeferToSpanScan`):
```go
base := alignDown(p, gc.PageSize)                        // база спана
objIndex := (p - base) * SizeClassToDivMagic[class] >> 32 // индекс объекта
```

#### Проблема классического маркера: локальность

🏛️ Классический `scanobject` ([`mgcmark.go`](src/runtime/mgcmark.go)) обходит граф **«по объектам»**: берёт один серый объект, идёт по его указателям, кладёт найденное в очередь. Указатели ведут «куда угодно», поэтому память трогается **хаотично**:
```
Очередь объектов (LIFO), адреса вперемешку:
  obj @0x00A100  (спан #7)
  obj @0xFF3400  (спан #941)   ← прыжок на другой конец кучи
  obj @0x00A140  (спан #7)     ← вернулись
  obj @0x7B2000  (спан #512)   ← опять улетели
```
Каждый прыжок = **промах кэша** (сотни тактов ожидания RAM), повторное чтение метаданных спана, невозможность prefetch. На современных CPU узкое место mark — это **ожидание памяти**, а не вычисления.

#### Что делает Green Tea

Идея из шапки файла: *«delay scanning so that we can accumulate objects to scan within the same span, then scan the objects that have accumulated on the span all together»*. То есть **в очередь кладутся не объекты, а целые спаны**, работа группируется по спанам:
```
Классика: очередь ОБЪЕКТОВ       Green Tea: очередь СПАНОВ (FIFO)
─────────────────────────       ─────────────────────────────────
obj @0x00A100                    спан #7   ─> [obj0, obj3, obj5, obj9]
obj @0xFF3400                    спан #941 ─> [obj2, obj7]
obj @0x00A140                    спан #512 ─> [obj1, obj4]
   ↑ прыжки по всей памяти          ↑ берём спан → сканируем всю
                                     пачку подряд, не выходя за 8 КБ
```

#### Механика: два набора бит (marks + scans)

🔧 Вместо одного mark-бита на объект Green Tea хранит **два** набора, встроенных прямо в спан (`spanInlineMarkBits`):
```go
type spanInlineMarkBits struct {
    scans [63]uint8         // "уже просканирован" (поля обойдены) ~ чёрный
    owned spanScanOwnership // захвачен ли спан для сканирования
    marks [63]uint8         // "обнаружен живым" (pre-mark)       ~ серый
    class spanClass
}
```

Алгоритм двухфазный:

**Фаза 1 — обнаружение** (`tryDeferToSpanScan`, строка 264). Увидев указатель впервые:
1. O(1)-арифметикой находит спан и индекс объекта.
2. Ставит **mark-бит** объекта.
3. **НЕ сканирует сразу** — ставит в очередь **весь спан** (`spanq.put`), захватив его через `tryAcquire()` (чтобы два P не поставили дважды).

Пока спан ждёт в очереди, другие маркировщики ставят mark-биты **другим объектам того же спана** — спан **накапливает пачку**.

**Фаза 2 — пакетное сканирование** (`scanSpan`, строка 844). Достав спан из очереди, вычисляет через операции над битами, кого сканировать, и сканирует **всю пачку подряд** в пределах 8 КБ:
```go
toScan := marks &^ scans   // диф: помечены, но ещё не сканированы
scans  |= marks            // union: отмечаем как сканированные
// ... сканируем все объекты из toScan, не выходя за спан
```
🏛️ Этот union/intersection-трюк даёт **precision**: ни один живой объект не потеряется и ни один не будет сканирован дважды.

#### Почему FIFO, а не LIFO

🔧 Очередь спанов — **FIFO** (обычные workbuf'ы — LIFO). Из комментария: *«a FIFO policy appears to work best for accumulating objects to scan on a span»*. FIFO даёт спану дольше «полежать» в очереди → накопить больше объектов → пачки жирнее → локальность лучше.

#### Что открывает пакетность

1. **Амортизация метаданных** — карта указателей спана читается один раз на весь спан, а не на каждый объект.
2. **Prefetch** — адреса объектов идут с фиксированным шагом по возрастанию → предсказуемы.
3. **SIMD** — для «плотных» спанов есть векторизованный путь `scan.ScanSpanPacked(...)`. Цель из комментария: *«applying SIMD techniques to really tear through the heap»*. Эвристика «dartboard»: если помечено мало (`objsMarked < nelems/8`), SIMD не окупается → разреженный путь `scanObjectsSmall`.
4. **Fast-track одиночек** — если на спане помечен ровно один объект (`spanScanOneMark`), дорогая merge-and-diff процедура пропускается, объект сканируется напрямую.

#### Итоговое сравнение

| | Классический маркер | Green Tea |
|---|---|---|
| Единица в очереди | отдельный **объект** | целый **спан** |
| Момент сканирования | сразу при обнаружении | **отложенно**, после накопления |
| Битов на объект | 1 (mark) | 2 (**marks** + **scans**) |
| Доступ к памяти | хаотичный, по всей куче | **локальный**, в пределах 8 КБ |
| Оптимизации | — | prefetch, амортизация метаданных, **SIMD** |
| Порядок очереди | LIFO | **FIFO** (лучше копит пачки) |

**Суть span-oriented:** вместо погони за каждым объектом по всей куче (плохая локальность, промахи кэша) Green Tea откладывает работу, **группирует объекты по их спанам** и сканирует каждый спан пачкой — упорядоченно, кэш-дружелюбно и с возможностью векторизации.

## 2. НАСТРОЙКА И ПОВЕДЕНИЕ

### 2.1. GOGC — главный «руль»

🏛️ **[ДИЗАЙН]** `GOGC` задаёт **компромисс между частотой сборок и потреблением памяти**. Значение по умолчанию — **100**.

**Смысл GOGC=100:** «запускай следующий цикл GC, когда объём живой кучи вырастет на 100% относительно размера живых данных после прошлой сборки». Иначе говоря — **когда куча удвоится**.

```
heap_goal = live_heap * (1 + GOGC/100)
```

Пример при `GOGC=100`:
- После сборки живых данных: 100 МБ.
- Цель (goal): 100 МБ × (1 + 100/100) = **200 МБ**.
- Когда куча дорастёт примерно до 200 МБ — стартует новый цикл.

🔧 Проверено в `src/runtime/mgcpacer.go`: `gcPercentHeapGoal = heapMarked + (heapMarked + stackScan + globalsScan) * gcPercent/100`. То есть в расчёт цели входит не только куча, но и объём стеков и глобалов для сканирования.

**Крутим руль:**
- `GOGC=200` → куча растёт втрое → GC реже → **меньше CPU на GC, но больше RAM**.
- `GOGC=50` → GC чаще → **больше CPU на GC, но экономнее по RAM**.
- `GOGC=off` (или `debug.SetGCPercent(-1)`) → **отключить** автоматический GC (только ручной `runtime.GC()`).

Из кода: `SetGCPercent(-1)` → внутри `gcPercent` становится `100000` (`src/runtime/mgcpacer.go:497`) — практически «никогда».

```go
import "runtime/debug"

func main() {
    debug.SetGCPercent(200)  // программно, эквивалент GOGC=200
}
```

🏛️ **Есть нижний предел:** `defaultHeapMinimum`. 🔧 Проверено в `mgcpacer.go`: **4 МБ** в обычной сборке (или 512 КБ при экспериментальном флаге `HeapMinimum512KiB`). GC не будет запускаться слишком часто на крошечных кучах, даже при агрессивном GOGC.

### 2.2. GOMEMLIMIT — soft memory limit

🔧 **[РЕАЛИЗАЦИЯ, с Go 1.19]** 📌 `GOMEMLIMIT` — **мягкий лимит памяти** для всего рантайма Go (в байтах; поддерживает суффиксы: `GOMEMLIMIT=4GiB`). По умолчанию — `off` (= `math.MaxInt64`, проверено в `mgcpacer.go:98`).

**Проблема, которую он решает.** До 1.19 существовала только относительная настройка (GOGC). Но в реальности у контейнера (k8s, Docker) есть **абсолютный** лимит RAM, за которым — OOM-kill. При всплеске живых данных GOGC-цель могла «выстрелить» выше лимита контейнера, и процесс убивали. А заранее занизить GOGC — значит зря жечь CPU в спокойное время.

**Как работает.** GOMEMLIMIT ставит потолок. По мере приближения потребления памяти к лимиту **pacer начинает запускать GC чаще и агрессивнее**, игнорируя GOGC-цель, лишь бы удержаться под лимитом.

🔧 Из кода `mgcpacer.go`: цель по памяти рассчитывается как `memoryLimitHeapGoal()`, и в `heapGoalInternal` берётся **минимум** из GOGC-цели и memory-limit-цели:
```go
if newGoal := c.memoryLimitHeapGoal(); newGoal < goal {
    goal = newGoal   // лимит памяти пересиливает GOGC
}
```
С запасом (headroom): `memoryLimitHeapGoalHeadroomPercent = 3` (%) и минимум `memoryLimitMinHeapGoalHeadroom = 1 МБ`.

**Взаимодействие GOGC + GOMEMLIMIT — рекомендуемый паттерн:**
```
GOGC=off  (или высокий)   +   GOMEMLIMIT=<почти весь лимит контейнера>
```
- В спокойное время GOGC высокий/выкл → GC редкий → экономим CPU.
- При росте нагрузки лимит «ловит» кучу → GC учащается → не даём OOM.

Типично ставят GOMEMLIMIT в ~90–95% от лимита контейнера, оставляя запас на не-heap память (стеки, mmap рантайма, cgo).

> ⚠️ **«Soft» — значит мягкий, не гарантия.** Если ваши **живые** данные реально превышают лимит, GC не может волшебно их сжать. В этом случае, чтобы не впасть в *GC death spiral* (сборщик крутится 100% CPU впустую), рантайм ограничивает долю CPU на GC (не более ~50%) и **позволит превысить лимит**, вместо того чтобы намертво зависнуть. Реальный OOM всё ещё возможен — GOMEMLIMIT защищает от всплесков, а не от нехватки памяти как таковой.

### 2.3. Чтение метрик GC

#### `GODEBUG=gctrace=1`

Самый быстрый способ увидеть работу GC — переменная окружения. 🔧 Формат вывода — деталь реализации, но структура стабильна:

```bash
GODEBUG=gctrace=1 ./myprogram
```
```
gc 14 @2.045s 3%: 0.018+1.9+0.023 ms clock, 0.14+0.31/1.8/0+0.18 ms cpu, 4->5->2 MB, 5 MB goal, 8 P
```

Разбор:
| Поле | Значение |
|---|---|
| `gc 14` | 14-й цикл GC с момента старта |
| `@2.045s` | время от старта программы |
| `3%` | **суммарная доля CPU**, потраченная на GC с начала работы |
| `0.018+1.9+0.023 ms clock` | фазы **по времени**: STW sweep termination + concurrent mark + STW mark termination |
| `0.14+0.31/1.8/0+0.18 ms cpu` | те же фазы в **CPU-времени** (по ядрам) |
| `4->5->2 MB` | куча: **до GC** → **пик в конце маркировки** → **живых после** |
| `5 MB goal` | целевой размер кучи (heap goal) для этого цикла |
| `8 P` | число процессоров (P), участвовавших |

**На что смотреть:**
- Первые два числа в `clock` (STW-паузы) должны быть **малы (доли/единицы мс)**. Если растут — проблема.
- Растущий процент CPU (`3%`) → GC ест слишком много → возможно, слишком много аллокаций или занижен GOGC.
- `4->5->2 MB`: если «живых после» (последнее число) быстро растёт — утечка/накопление; если пик (среднее) намного больше живых — много «мусора-однодневок».

#### `runtime.MemStats` — программный доступ

```go
import (
    "runtime"
    "fmt"
)

func printGCStats() {
    var m runtime.MemStats
    runtime.ReadMemStats(&m)   // ВНИМАНИЕ: делает короткий STW! Не в горячем цикле.

    fmt.Printf("HeapAlloc   = %v MB\n", m.HeapAlloc/1024/1024)  // сейчас занято живыми
    fmt.Printf("HeapSys     = %v MB\n", m.HeapSys/1024/1024)    // зарезервировано у ОС
    fmt.Printf("HeapObjects = %v\n",    m.HeapObjects)          // число объектов
    fmt.Printf("NumGC       = %v\n",    m.NumGC)                // сколько было циклов
    fmt.Printf("PauseTotalNs= %v\n",    m.PauseTotalNs)         // сумма всех STW-пауз
    fmt.Printf("GCCPUFraction = %.4f\n", m.GCCPUFraction)       // доля CPU на GC (0..1)
    fmt.Printf("NextGC      = %v MB\n", m.NextGC/1024/1024)     // heap goal
    fmt.Printf("Mallocs=%v Frees=%v\n", m.Mallocs, m.Frees)     // всего аллокаций/освобождений
}
```

> 🔧 **[РЕАЛИЗАЦИЯ]** Для продакшн-мониторинга предпочтителен пакет **`runtime/metrics`** (с Go 1.16) — он даёт метрики без полного STW `ReadMemStats` и с более стабильным API (например, `/gc/heap/goal:bytes`, `/gc/pauses:seconds` в виде гистограммы, `/memory/classes/*`).

```go
import "runtime/metrics"

samples := []metrics.Sample{
    {Name: "/gc/heap/goal:bytes"},
    {Name: "/gc/cycles/total:gc-cycles"},
}
metrics.Read(samples)
```

### 2.4. Pacer — «кардиостимулятор» сборщика

🏛️ **[ДИЗАЙН, но конкретная формула — деталь реализации]** **Pacer** решает две задачи:
1. **КОГДА** запускать цикл GC (в какой момент роста кучи).
2. **С КАКОЙ ИНТЕНСИВНОСТЬЮ** маркировать и **сколько assist** навешивать на аллоцирующие горутины.

**Цель pacer’а:** завершить маркировку ровно к тому моменту, когда куча дорастёт до `heap_goal`. Не слишком рано (зря потрачен CPU, память недоиспользована) и не слишком поздно (куча проскочит цель).

**Триггер (когда стартовать).** Pacer стартует GC **раньше** достижения цели, оставляя время на конкурентную маркировку. Он оценивает: «при текущей скорости аллокации и скорости маркировки, чтобы финишировать к goal — начать надо при размере кучи X». 🔧 В `mgcpacer.go` это `trigger` — вычисляется из истории предыдущих циклов (сколько маркировали, как быстро росла куча) с ограничением `maxTrigger`.

**Обратная связь.** Pacer — это, по сути, **пропорциональный контроллер (control loop)**: после каждого цикла он смотрит, промахнулся ли мимо цели, и корректирует параметры следующего. Если куча раз за разом «проскакивает» goal — он либо стартует раньше, либо усиливает mark assist.

```
       скорость аллокации (mutator)
                 │
                 ▼
  ┌────────────────────────────┐
  │  PACER (control loop)       │
  │  • оценить trigger          │◄── история прошлых циклов
  │  • рассчитать assist ratio  │    (heapMarked, длит. маркировки)
  └────────────────────────────┘
       │                    │
       ▼                    ▼
  когда стартовать      сколько mark assist
  цикл GC               навесить на горутины
```

🔧 Текущий pacer — это **редизайн, вошедший в Go 1.18** (более простая и предсказуемая модель, чем в 1.5–1.17). Это деталь реализации: формулы менялись и ещё будут меняться.

## 3. ЭВОЛЮЦИЯ GC ПО ВЕРСИЯМ

> Ниже — вехи. 🏛️ отмечает изменения дизайна, 🔧 — крупные детали реализации. Точные цифры пауз из ранних анонсов приводятся как исторический контекст.

### Go 1.3 (2014) — точная маркировка
Переход к **precise GC** для кучи: рантайм точно знает, где указатели (раньше стек сканировался консервативно). Фундамент для будущей конкурентности. Аллокатор — на базе TCMalloc.

### Go 1.5 (2015) — 🏛️ рождение конкурентного GC
**Поворотный релиз.** Полностью переписанный **concurrent tri-color mark-and-sweep**. Заявленная цель — паузы **< 10 мс**, и вскоре суб-миллисекундные для многих нагрузок.
- **Почему:** прежний STW-сборщик давал паузы в **сотни миллисекунд** на больших кучах — неприемлемо для сервисов Google.
- Введены mark assist, dedicated worker’ы (~25% CPU), pacer первой версии.

### Go 1.6–1.7 (2016) — шлифовка
Снижение пауз на больших кучах; часть работы mark termination вынесена из STW. Паузы на многогигабайтных кучах опустились до единиц мс.

### Go 1.8 (2017) — 🏛️ гибридный барьер, устранение re-scan стеков
**Ключевейший релиз для латентности.** Внедрён **hybrid write barrier** (Yuasa + Dijkstra), что **устранило повторное STW-сканирование стеков** в конце цикла.
- **Почему:** до этого mark termination повторно сканировал стеки всех горутин под STW — это и давало «длинные хвосты» пауз (могли доходить до 10+ мс при многих горутинах).
- **Результат:** типичные STW-паузы упали до **< 100 микросекунд** (сотни µs → десятки µs). Проверено, что этот барьер по-прежнему в `src/runtime/mbarrier.go` в 1.26.

### Go 1.12 (2019) — 🔧 улучшенный sweep, освобождение памяти ОС
Улучшена возвращаемость памяти ОС; ранее — переход на `MADV_FREE` (потом переосмыслен в 1.16 в пользу более предсказуемого `MADV_DONTNEED` на Linux — из-за путаницы в метриках RSS у пользователей).

### Go 1.14 (2020) — 🏛️ асинхронная вытесняющая приостановка (async preemption)
Горутины теперь можно **вытеснить асинхронно** (по сигналу), а не только в safe-points на вызовах функций. GC (и планировщик) больше не «застревают», ожидая горутину в тесном цикле без вызовов.
- **Почему:** плотный цикл `for {}` без вызовов мог задерживать STW-фазы на неопределённое время.

### Go 1.18 (2022) — 🔧 редизайн pacer
Новый, более простой и предсказуемый pacer. Лучше поведение при резких сменах скорости аллокации; убраны краевые случаи «пилообразного» поведения старого контроллера.

### Go 1.19 (2022) — 📌 🏛️ GOMEMLIMIT (soft memory limit)
Добавлен **мягкий лимит памяти** `GOMEMLIMIT` / `debug.SetMemoryLimit`.
- **Почему:** массовый переход в контейнеры. Нужен был способ жёстко ограничить память сверху, не жертвуя CPU через постоянно заниженный GOGC. Решает проблему OOM-kill при всплесках. (Детали — §2.2.)

### Go 1.20–1.23 — 🔧 инкрементальные улучшения
Оптимизации аллокатора, внутренних структур, снижение оверхеда write barrier, улучшения `runtime/metrics`, доработки поведения возврата памяти ОС и pacer в краевых случаях.

### 📌 Go 1.25 (2025) — 🔧 Green Tea GC (эксперимент)
Появился **Green Tea GC** — новый **span-ориентированный маркировщик**, ориентированный на локальность памяти. Включался через `GOEXPERIMENT=greenteagc`.
- **Почему:** на современных многоядерных CPU узкое место фазы mark — **пропускная способность памяти и промахи кэша**, а не арифметика. Классический маркировщик обходит граф «по объектам», прыгая по всей куче хаотично. Green Tea меняет это на пакетную поспановую обработку.
- Подробный разбор механики — см. **§1.7 «Green Tea GC»** ниже. Здесь — только историческая веха.

### 📌 Go 1.26 (текущая, 1.26.4) — 🔧 Green Tea GC ВКЛЮЧЁН ПО УМОЛЧАНИЮ
**Проверено в исходниках этой копии** (`src/internal/buildcfg/exp.go`):
```go
baseline := goexperiment.Flags{
    ...
    GreenTeaGC: true,   // ← включён в baseline по умолчанию
    ...
}
```
Также подтверждено в `src/runtime/mgcpacer.go` и `mgc.go` наличие веток `if goexperiment.GreenTeaGC { ... }` (например, создание worker’ов маркировки из idle-P).
- 🏛️ **Важно:** несмотря на смену *механики маркировки*, фундаментальные свойства сохранены: сборщик остаётся **concurrent, non-moving, non-generational, tri-color mark-and-sweep** с гибридным write barrier. Green Tea — это оптимизация *как физически обходится память* на фазе mark, а не смена парадигмы. Полное описание — в **§1.7**.

> ⚠️ Для самых свежих и точных цифр всегда сверяйтесь с официальными **Release Notes** (go.dev/doc/devel/release), блогом Go (go.dev/blog) и design-документами в `src/runtime/` (файлы `mgc.go`, `mbarrier.go`, `mgcpacer.go`, `mgcmark.go`, `mgcmark_greenteagc.go` содержат подробнейшие комментарии).

## 4. СРАВНЕНИЕ С ДРУГИМИ ЯЗЫКАМИ

🏛️ Каждый GC живёт в **треугольнике компромиссов**:

```
              LATENCY (низкая задержка/паузы)
                       ▲
                      / \
                     /   \
                    /  Go \        Go тянет сюда: минимальные паузы
                   /       \
                  /         \
   THROUGHPUT ◄──┴───────────┴──► FOOTPRINT
   (пропускная                    (расход памяти)
    способность)
```
Нельзя выиграть во всех трёх сразу. **Go осознанно жертвует пропускной способностью и отчасти footprint ради предсказуемо низких пауз.**

### 4.1. Java (JVM)

🏛️ JVM — «зоопарк» сборщиков на выбор, все **generational + (в основном) moving/compacting**:

| Сборщик | Тип | Профиль | Паузы |
|---|---|---|---|
| **Parallel GC** | generational, STW, compacting | максимум throughput | длинные (десятки-сотни мс) |
| **G1** (default с Java 9) | generational, регионный, частично concurrent, compacting | баланс | ~сотни µs – единицы мс |
| **ZGC** | concurrent, **read barriers**, colored pointers, регионный, moving | сверхнизкие паузы | **< 1 мс** даже на терабайтных кучах |
| **Shenandoah** | concurrent, compacting, Brooks/read barriers | низкие паузы | < мс |

**Ключевые отличия от Go:**
- 🏛️ **Поколенческий.** JVM эксплуатирует «умирают молодыми»: minor GC собирает молодое поколение часто и очень эффективно (bump-pointer аллокация + копирование выживших). Go этого не делает, полагаясь на escape analysis + стек.
- 🏛️ **Compacting/moving.** JVM **перемещает** объекты (копирование выживших, дефрагментация). Это даёт **аллокацию за O(1)** (просто сдвиг указателя в непрерывной области — «bump pointer») и ноль фрагментации. Плата: нужно обновлять указатели → либо STW, либо **read barriers** (ZGC/Shenandoah), которые дороже write barrier’ов Go.
- **ZGC vs Go по паузам** сопоставимы (суб-миллисекунда), но ZGC достигает этого ценой read-барьеров и большего footprint; Go — ценой отсутствия compaction (риск фрагментации) и non-generational (больше работы маркировки на больших живых кучах).

**Компромисс:** JVM (особенно Parallel/G1) обычно даёт **бóльшую пропускную способность** и лучшую утилизацию памяти на больших долгоживущих кучах, но исторически — бóльшие или менее предсказуемые паузы (кроме ZGC/Shenandoah). Go проще в эксплуатации: **один сборщик, две ручки (GOGC/GOMEMLIMIT)** против десятков JVM-флагов.

### 4.2. C# / .NET

🏛️ CLR GC — **generational (3 поколения: Gen0, Gen1, Gen2 + LOH — Large Object Heap), compacting, tracing**.

Два режима:
- **Workstation GC:** для десктоп/клиентских приложений. Меньше потоков, оптимизирован под отзывчивость одного приложения.
- **Server GC:** для серверов. **Отдельная куча и GC-поток на каждый CPU** → высокая параллельность и throughput. Плюс **Background GC** для Gen2 — конкурентная сборка старого поколения без длинных пауз.

**Отличия от Go:**
- Как и JVM — **поколенческий и сжимающий**: Gen0 (молодые) собирается очень часто и дёшево; выжившие продвигаются в Gen1→Gen2. Bump-pointer аллокация.
- Есть отдельная **LOH** для больших объектов (аналогия с large-спанами Go), которая по умолчанию **не компактится** (можно принудительно).
- Философия .NET ближе к JVM: **throughput-oriented с конфигурируемой конкурентностью**, тогда как Go — **latency-first by default**.

**Компромисс:** Server GC даёт отличную пропускную способность на многоядерных серверах; но настройка сложнее, а поведение поколений/компакции менее «прозрачно», чем предсказуемый один-сборщик-Go.

### 4.3. Python (CPython)

🏛️ Принципиально **другой подход**: **reference counting (подсчёт ссылок)** как основной механизм + **циклический сборщик** как дополнение.

**Reference counting:**
```python
a = []        # у объекта-списка refcount = 1
b = a         # refcount = 2
del b         # refcount = 1
del a         # refcount = 0 → объект НЕМЕДЛЕННО освобождается
```
Каждый объект хранит счётчик ссылок. Присваивание +1, удаление ссылки −1. Как только счётчик = 0 — память освобождается **сразу, детерминированно**.

**Отличия от трассирующего GC Go:**

| | CPython (refcount) | Go (tracing) |
|---|---|---|
| Момент освобождения | **детерминированный** (сразу при refcount=0) | недетерминированный (когда решит GC) |
| Паузы | «размазаны» по каждой операции с указателем | сконцентрированы в циклах GC (но крошечные) |
| Циклы ссылок | ❌ refcount **не ловит** (A→B→A даёт вечный refcount≥1) | ✅ ловятся естественно (недостижимы от корней) |
| Оверхед | счётчик на **каждую** операцию + промахи кэша | write barrier только во время маркировки |
| Многопоточность | требует **GIL** (или сложной атомарности) | нативно конкурентный |

**Циклический сборщик** CPython существует именно чтобы добивать **ссылочные циклы**, которые refcount пропускает. Это отдельный поколенческий tracing-GC поверх refcount.

**Компромисс:** refcount прост и детерминирован (хорош для RAII-подобных паттернов, `with`), но его цена — постоянный оверхед на счётчики и историческая привязка к **GIL**, ограничивающая многопоточность. Go’s tracing масштабируется на многие ядра, но освобождение недетерминированно. (Замечу: в Python 3.12+ идёт работа над no-GIL/immortal objects, что меняет картину.)

### 4.4. Rust — GC нет вообще

🏛️ Rust **не имеет сборщика мусора** и не имеет ручного `malloc/free` в обычном коде. Память управляется **на этапе компиляции** через систему типов:

- **Ownership (владение):** у каждого значения ровно один владелец. Когда владелец выходит из области видимости — значение автоматически освобождается.
- **Borrow checker (проверка заимствований):** ссылки (`&T`, `&mut T`) проверяются компилятором на отсутствие висячих указателей и гонок данных. Правило: либо много читателей, либо один писатель.
- **RAII (Resource Acquisition Is Initialization):** освобождение привязано к области видимости через типаж `Drop` — детерминированно, как деструкторы C++.
- **Lifetimes (времена жизни):** компилятор доказывает, что ссылка не переживёт данные, на которые указывает.

```rust
fn example() {
    let s = String::from("hello"); // s владеет памятью в куче
    let len = s.len();
    // ... используем s ...
} // <- здесь s выходит из scope → Drop → память освобождается СРАЗУ.
  //    Никакого GC, никаких пауз, всё решено на компиляции.
```

**Отличия от Go:**
- 🏛️ **Zero runtime cost:** нет ни sweeper’а, ни write barrier, ни STW-пауз, ни фонового потока GC. Идеально для realtime, embedded, ядер ОС.
- Для случаев, где владение недостаточно (разделяемое владение, циклы), есть **`Rc`/`Arc`** (reference counting, как у Python, но опциональный и явный) и `Weak` для разрыва циклов.

**Компромисс:**
- ✅ Максимальный контроль, минимальный footprint, **предсказуемость без пауз**, лучший throughput среди упомянутых.
- ❌ **Высокая когнитивная нагрузка на программиста** (борьба с borrow checker), более медленная разработка, некоторые структуры данных (графы, двусвязные списки) реализуются сложно/через `unsafe` или `Rc<RefCell<>>`.

**Почему Go выбрал GC, а не путь Rust:** 🏛️ приоритет Go — **простота и скорость разработки**, лёгкая конкурентность (горутины), быстрая компиляция. GC избавляет программиста от целого класса ошибок памяти *без* налога сложности borrow checker’а. Это осознанный обмен: немного runtime-оверхеда и пауз в обмен на радикальную простоту.

### 4.5. Сводная таблица

| Язык | Тип управления памятью | Generational | Moving | Паузы | Главный приоритет |
|---|---|---|---|---|---|
| **Go** | Concurrent tracing M&S | ❌ | ❌ | сверхнизкие (µs) | **latency + простота** |
| **Java (G1/ZGC)** | Concurrent tracing | ✅ | ✅ | мс / <мс (ZGC) | throughput / tunable |
| **C#/.NET** | Generational tracing | ✅ | ✅ | низкие (Server+BG) | throughput / tunable |
| **Python** | Refcount + cyclic GC | ✅ (циклы) | ❌ | размазаны + GIL | детерминизм / простота |
| **Rust** | Ownership (compile-time) | — | — | **нет** | контроль / zero-cost |

**Итог по Go:** он сознательно занял нишу «**предсказуемо низкие паузы + минимум ручек настройки**», пожертвовав пиковым throughput (write barrier, отсутствие поколений) и оптимальным footprint (отсутствие compaction, куча растёт до ~2× живых данных при GOGC=100). Для его целевой аудитории — сетевые сервисы и инфраструктура — это правильный размен.

## 5. ПРАКТИКА

### 5.1. Типичные проблемы производительности из-за GC

1. **Слишком много аллокаций (allocation churn).** Главная причина нагрузки на GC. Каждая аллокация приближает следующий цикл. Часто — «невидимые» аллокации: конкатенация строк в цикле, `append` без предвыделения, боксинг в `interface{}`.
2. **GC ест высокий % CPU** (видно в `gctrace` или `GCCPUFraction`). Обычно следствие п.1 или заниженного GOGC.
3. **Всплески памяти → OOM** в контейнерах (лечится GOMEMLIMIT).
4. **Задержки от mark assist:** при быстрой аллокации горутины вынуждены «отрабатывать долг» маркировкой → растёт latency именно у горячих путей.
5. **Ложные утечки:** объект достижим через забытую ссылку (slice, держащий большой backing array; глобальная мапа-кэш без вытеснения; незакрытый канал/горутина).

### 5.2. Диагностика: pprof и trace

#### pprof — профиль аллокаций (главный инструмент против GC-нагрузки)

Подключение HTTP-профайлера:
```go
import (
    "net/http"
    _ "net/http/pprof"   // регистрирует /debug/pprof/*
)

func main() {
    go func() { http.ListenAndServe("localhost:6060", nil) }()
    // ... остальная программа ...
}
```

Снять и посмотреть профиль **кучи/аллокаций**:
```bash
# профиль по объёму аллокаций за всё время (что грузит GC):
go tool pprof http://localhost:6060/debug/pprof/allocs

# внутри pprof:
(pprof) top          # топ функций по аллокациям
(pprof) list <func>  # построчно, где именно аллоцируется
(pprof) web          # граф (нужен graphviz)
```

Ключевые метрики:
- `alloc_space` / `alloc_objects` — **сколько всего аллоцировано** (нагрузка на GC, даже если уже освобождено). ← смотреть это для оптимизации GC.
- `inuse_space` / `inuse_objects` — **сколько живёт сейчас** (для поиска утечек).

В бенчмарках:
```bash
go test -bench=. -benchmem            # покажет B/op и allocs/op
go test -bench=. -memprofile=mem.out
go tool pprof mem.out
```

#### runtime/trace — временная шкала GC

```go
import (
    "os"
    "runtime/trace"
)

func main() {
    f, _ := os.Create("trace.out")
    trace.Start(f)
    defer trace.Stop()
    // ... нагрузка ...
}
```
```bash
go tool trace trace.out   # откроет браузер
```
В трейсе видно: когда шли GC-циклы, длительность STW, сколько времени горутины провели в **mark assist**, конкуренцию за P. Идеально, чтобы увидеть, что GC — источник latency-спайков.

### 5.3. Приёмы снижения нагрузки на GC

#### (1) `sync.Pool` — переиспользование объектов

🔧 Пул временных объектов, переживающий отдельные операции. Особенно эффективен для буферов в высоконагруженных обработчиках.

```go
import "sync"

var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func handle(w io.Writer, data []byte) {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()                 // ВАЖНО: очистить перед использованием
    defer bufPool.Put(buf)      // вернуть в пул

    buf.Write(data)
    // ... работа с buf ...
    w.Write(buf.Bytes())
}
```
> ⚠️ Объекты в `sync.Pool` **могут быть удалены GC** между циклами (пул — не кэш с гарантией). Не храните там то, что обязано жить. Используйте для *временных* объектов на горячем пути. Не забывайте `Reset()`.

#### (2) Предвыделение слайсов/мап (capacity hints)

Каждый рост `append` за пределы capacity → новая аллокация + копирование. Если размер известен/оценим:
```go
// ПЛОХО: многократный реаллок по мере роста
var s []int
for i := 0; i < n; i++ { s = append(s, i) }

// ХОРОШО: одна аллокация
s := make([]int, 0, n)          // capacity = n сразу
for i := 0; i < n; i++ { s = append(s, i) }

// Аналогично для map:
m := make(map[string]int, n)    // подсказка размера
```

#### (3) Переиспользование буферов

```go
// Переиспользуем один буфер между итерациями вместо аллокации в цикле:
buf := make([]byte, 0, 4096)
for _, item := range items {
    buf = buf[:0]               // сброс длины, capacity сохраняется (0 аллокаций)
    buf = appendEncode(buf, item)
    out.Write(buf)
}
```

#### (4) Value vs Pointer semantics

🏛️ Указатели почти всегда означают аллокацию в куче (escape) + нагрузку на GC + разыменование (промах кэша). Значения могут жить на стеке и не касаться GC.

```go
type Point struct{ X, Y float64 }

// Значение — вероятно на стеке, не грузит GC, дружелюбно к кэшу:
func distance(a, b Point) float64 { ... }

// Указатель — заставляет объект "убежать" в кучу:
func distancePtr(a, b *Point) float64 { ... }
```

**Особый выигрыш — слайсы значений vs слайсы указателей:**
```go
// []T — один непрерывный блок, отличная локальность, МАЛО объектов для GC:
points := make([]Point, 1000)      // 1 аллокация, 0 указателей для сканирования

// []*T — 1000 отдельных объектов в куче + слайс указателей:
ptrs := make([]*Point, 1000)       // GC обходит 1000 указателей + 1000 объектов
for i := range ptrs { ptrs[i] = &Point{} }
```
🏛️ **Правило:** если в структуре/слайсе **нет указателей**, GC-маркировщику вообще нечего в ней сканировать (спан помечается как «noscan»). Уменьшение числа указателей = прямое уменьшение работы маркировки. Это одна из причин, почему `[]Point` радикально дешевле для GC, чем `[]*Point`.

#### (5) Проектирование против «убегания» в кучу

- Возвращайте значения, а не указатели, для маленьких структур.
- Избегайте лишнего `interface{}`/`any` на горячем пути (боксинг → escape).
- Не берите `&local`, если можно вернуть значение.
- Проверяйте гипотезы через `go build -gcflags='-m'`.

#### (6) Настройка ручек под нагрузку

```go
import "runtime/debug"

func main() {
    // Сервис с большим запасом RAM, важен throughput → реже GC:
    debug.SetGCPercent(300)

    // В контейнере с лимитом 2 GiB — защита от OOM:
    debug.SetMemoryLimit(1900 * 1024 * 1024)  // ~1.9 GiB, оставляем запас
}
```
Или через окружение (без изменения кода):
```bash
GOGC=300 GOMEMLIMIT=1900MiB ./myservice
```

#### (7) Golden rule оптимизации

1. **Сначала измерь** (`-benchmem`, pprof `allocs`, `gctrace`). Не оптимизируй вслепую.
2. Найди **топ-аллокаторы** и убери самые жирные.
3. `sync.Pool` — не первое, а последнее средство: сложность и подводные камни. Сначала — предвыделение и value-семантика.
4. Перепроверь после изменений: стало ли меньше `allocs/op` и `GCCPUFraction`.

## 6. Резюме: дизайн vs реализация

### 🏛️ Фундаментальный дизайн (стабильно годами)
- Concurrent **tri-color mark-and-sweep**.
- **Non-generational, non-moving/non-compacting**.
- **Hybrid write barrier** (Yuasa + Dijkstra) → без re-scan стеков.
- Приоритет — **низкая задержка**, а не throughput.
- Аллокатор на базе **TCMalloc** (mcache/mcentral/mheap, size classes, спаны).
- **Escape analysis** уводит недолговечные объекты на стек.
- Управление — двумя ручками: **GOGC** (относительная) и **GOMEMLIMIT** (абсолютная).
- Обратная связь через **mark assist** («загрязнитель платит»).

### 🔧 Детали реализации (меняются между версиями)
- Конкретные формулы **pacer’а** (редизайн в 1.18).
- **Число и границы size classes** (~68, MaxSmallSize=32 КБ, page=8 КБ в 1.26).
- `defaultHeapMinimum` (4 МБ в обычной сборке 1.26).
- Целевые % CPU на GC (~25% worker’ов).
- Формат вывода `gctrace`.
- Стратегия возврата памяти ОС (`MADV_DONTNEED`/`MADV_FREE`).
- 📌 **Green Tea GC** — новый span-ориентированный маркировщик, **включён по умолчанию в Go 1.26** (проверено: `GreenTeaGC: true` в `src/internal/buildcfg/exp.go`).
