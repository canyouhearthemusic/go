## TL;DR

- **История:** до 1.23 — хеш-таблица с бакетами и цепочками overflow. **1.24** — Swiss Table по умолчанию, старая доступна через `GOEXPERIMENT=noswissmap`. **1.26** — старая удалена совсем (коммит `2ae059ccaf`).
- **Старая:** массив из `2^B` бакетов по 8 пар; бакет выбирают **младшие** биты хеша; переполнение — отдельный overflow-бакет по указателю; рост — постепенный перенос (эвакуация) при каждой записи.
- **Swiss:** группы по 8 слотов + 8-байтовое control word; 7 бит хеша (H2) лежат в control word, поэтому 8 слотов проверяются **одной операцией**; коллизии — пробирование соседних групп, overflow-указателей нет.
- **Рост в swiss:** карта = каталог из таблиц, таблица ≤ 1024 слотов. Таблица растёт целиком, но она маленькая → нет долгой паузы и не нужна эвакуация.
- **Загрузка:** старая — 6.5 элементов на бакет (≈81%), swiss — 7/8 (87.5%).
- **Маленькая карта (≤ 8 элементов)** в swiss — одна группа без таблиц; если не убегает — живёт на стеке.
- **Не изменилось:** карта не уменьшается после `delete`; порядок обхода случайный; конкурентная запись — `fatal error`, не `panic`; ключи/значения > 128 байт хранятся по указателю.
- **Замер (1M `int64→int64`, go1.25 old vs swiss):** промах поиска 31.9 → 22.5 ns, вставка без hint 78 → 45 ms, память 38.3 → 36.0 MiB.

## 0. Словарь

| Термин | Что значит |
|---|---|
| **хеш** | число из ключа; по нему решается, куда положить пару |
| **seed** | случайная «соль» хеша, своя у каждой карты — защита от подбора коллизий |
| **коллизия** | два ключа претендуют на одно место |
| **бакет (bucket, `bmap`)** | старая реализация: ящик на 8 пар + ссылка на следующий ящик |
| **overflow-бакет** | дополнительный ящик, подвешенный к переполненному |
| **tophash** | верхний байт хеша, хранится в бакете как быстрый фильтр |
| **группа (group)** | swiss: 8 слотов + control word |
| **control word** | 8 байт, по байту на слот: пусто / удалено / занято + H2 |
| **H1 / H2** | старшие 57 бит хеша / младшие 7 бит |
| **пробирование (probing)** | если место занято — проверяем следующую группу по формуле |
| **tombstone** | метка «здесь удалили», чтобы поиск не остановился раньше времени |
| **load factor** | насколько таблица заполнена перед ростом |
| **эвакуация** | старая: перенос пар из старого массива бакетов в новый по кусочку |
| **каталог (directory)** | swiss: массив указателей на таблицы |
| **SIMD / SWAR** | обработка нескольких байт одной инструкцией (SIMD — спец. инструкции, SWAR — трюк обычной арифметикой на `uint64`) |

## 1. Старая реализация (Go ≤ 1.23)

> **Простыми словами.** Есть ряд из `2^B` ящиков. Хеш ключа говорит номер ящика. В ящике 8 мест. Если места кончились — к ящику цепляется ещё один ящик. Когда ящиков мало, заводится ряд вдвое длиннее, и вещи переносятся туда понемногу, при каждой записи.

### 1.1 Структура

```text
hmap                                         bmap (бакет)
┌─────────────┐                              ┌──────────────────────────┐
│ count       │  len(m)                      │ tophash [8]uint8         │
│ flags       │  writing/iterator/...        │ keys    [8]K             │ ← сначала все ключи,
│ B           │  log2(числа бакетов)         │ elems   [8]V             │ ← потом все значения
│ noverflow   │  ≈ число overflow-бакетов    │ overflow *bmap ──────────┼──► ещё бакет
│ hash0       │  seed                        └──────────────────────────┘
│ buckets ────┼──► [2^B]bmap
│ oldbuckets ─┼──► [2^(B-1)]bmap  (≠nil только во время роста)
│ nevacuate   │  сколько старых бакетов уже перенесено
└─────────────┘
```

Ключи и значения лежат раздельно (`KKKKKKKKVVVVVVVV`), а не парами: для `map[int64]int8` так нет выравнивающих дыр.

### 1.2 Поиск

```text
hash = hash(key, hash0)
номер бакета = hash & (2^B - 1)          ← младшие B бит
top          = hash >> 56 (если < 5, то +5) ← значения 0..4 заняты служебными метками
в бакете и его overflow-цепочке: для i in 0..7
    tophash[i] == top ? → сравнить сам ключ
    tophash[i] == emptyRest ? → дальше пусто, ключа нет
```

Метки tophash (`map_noswiss.go`): `emptyRest=0`, `emptyOne=1`, `evacuatedX=2`, `evacuatedY=3`, `evacuatedEmpty=4`, `minTopHash=5`.

### 1.3 Рост

Два триггера (проверяются при вставке нового ключа):

| Условие | Код | Что делает |
|---|---|---|
| `count > 6.5 · 2^B` | `overLoadFactor` | **удвоение**: `B+1` |
| `noverflow ≥ 2^min(B,15)` | `tooManyOverflowBuckets` | **рост того же размера** (`sameSizeGrow`): переупаковать цепочки, оставшиеся после удалений |

Рост **инкрементальный**: `hashGrow` только выделяет новый массив. Дальше каждая запись/удаление вызывает `growWork` — переносит бакет, в который пишем, и ещё один по счётчику `nevacuate`. При удвоении пары старого бакета `i` расходятся в `i` (X) или `i + 2^oldB` (Y) по одному новому биту хеша.

Почему 6.5 — из комментария в исходнике (таблица для 8-байтных ключей/значений при максимальной загрузке):

| load factor | % бакетов с overflow | байт оверхеда/запись |
|---|---|---|
| 6.0 | 15.3 | 11.7 |
| **6.5** | **20.9** | **10.8** |
| 7.0 | 27.1 | 10.2 |

### 1.4 Цена

- overflow-бакет — отдельная аллокация и переход по указателю (промах кэша);
- tophash проверяется по одному байту в цикле;
- во время роста каждый поиск может смотреть и в `oldbuckets`, а каждая запись делает лишнюю работу;
- итератор обязан учитывать «полуперенесённое» состояние — сложный код.

**Что важно для Senior**
- Бакет выбирают младшие биты, tophash — старший байт; 8 пар на бакет, load factor 6.5.
- Рост размазан по записям: нет одной большой паузы, но поиск во время роста дороже.
- `sameSizeGrow` лечит длинные цепочки после массовых удалений, но памяти не отдаёт.

## 2. Swiss Table (Go 1.24+)

> **Простыми словами.** Ящиков-цепочек больше нет. Есть длинная полка из групп по 8 мест. У каждой группы — «табличка» из 8 байт, где про каждое место написано: пусто, удалено, или занято ключом с такими-то 7 битами хеша. Процессор сравнивает всю табличку разом и сразу видит, в каких местах *может* быть наш ключ. Если группа полна — идём к следующей группе по формуле. Большую карту режут на много небольших таблиц, и растёт каждая сама по себе.

### 2.1 Структура

```text
Map                                   table (≤ 1024 слотов)
┌──────────────────┐                  ┌──────────────┐
│ used             │ len(m)           │ used         │
│ seed             │                  │ capacity     │ слотов, 2^N
│ dirPtr ──────────┼─► [ *table ...]  │ growthLeft   │ сколько ещё вставить до роста
│ dirLen           │   каталог        │ localDepth   │
│ globalDepth      │                  │ groups ──────┼─► [group][group]...
│ writing          │                  └──────────────┘
│ tombstonePossible│
│ clearSeq         │      group:  [ctrl 8 байт][slot0: K V][slot1: K V] ... [slot7: K V]
└──────────────────┘
```

По умолчанию слот = пара ключ+значение подряд (`KVKV…`). В 1.27 появился `GOEXPERIMENT=mapsplitgroup` с раскладкой `KKKKVVVV`, как в старой реализации; по умолчанию выключен (нет в `buildcfg/exp.go`).

**Маленькая карта:** пока элементов ≤ 8, `dirLen == 0` и `dirPtr` указывает прямо на одну группу — без таблицы и каталога. Если карта не убегает из функции, компилятор кладёт эту группу на стек (с 1.24, коммит `63ba2b9d84`):

```go
func countStatuses(codes []int) int {
	seen := make(map[int]bool) // ≤8 записей — одна группа
	for _, c := range codes {
		seen[c] = true
	}
	return len(seen)
}
```

```text
$ go build -gcflags=-m .
./main.go:4:14: make(map[int]bool) does not escape
```

### 2.2 Control word

```text
1 0000000  ctrlEmpty   (0x80)  пусто
1 1111110  ctrlDeleted (0xFE)  tombstone
0 hhhhhhh  занято, hhhhhhh = H2 (младшие 7 бит хеша)
```

Поиск в группе: размножить H2 на все 8 байт, XOR с control word, найти нулевые байты — это `matchH2` (`group.go`). Результат — битовая маска кандидатов. На **amd64** это SIMD-интринсик (с 1.24, коммит `dce30a1920`), на остальных архитектурах — SWAR-трюк на `uint64`. Ложное совпадение — 1/128 на слот, поэтому кандидат всё равно сверяется полным сравнением ключа.

### 2.3 Поиск

```text
hash = hash(key, seed)
таблица  = каталог[hash >> (64 - globalDepth)]   ← старшие биты
H1 = hash >> 7,  H2 = hash & 0x7f
группа   = H1 & mask; дальше пробирование: +1, +2, +3 ... (треугольные числа)
в группе: matchH2 → сравнить ключи кандидатов
          есть ctrlEmpty → ключа нет, стоп
```

Пробирование квадратичное (`p(i) = H1 + (i²+i)/2 mod groups`); при числе групп = степень двойки оно обходит каждую группу ровно один раз (`probeSeq`, `table.go`). Таблица никогда не заполняется на 100%, поэтому пустой слот на пути всегда найдётся.

### 2.4 Удаление и tombstone

Поиск останавливается на группе с пустым слотом. Значит:
- в группе есть пустой слот → удаляемый слот просто помечается пустым;
- группа была полной → ставится **tombstone** (иначе поиск ключа, который «проскочил» эту группу при вставке, остановится раньше и не найдёт его).

Вставка сначала занимает tombstone. Tombstone считаются в загрузке. Когда место кончилось (`growthLeft == 0`), с **1.25** сначала пробуется `pruneTombstones` (если tombstone ≥ 10% ёмкости), и только потом рост. Перестановка «на месте» (как в Abseil) не делается — она ломает итерацию (TODO в `rehash`).

### 2.5 Рост: extendible hashing

```text
вставка, места нет
   │
   ├── capacity·2 ≤ 1024 → grow: новая таблица вдвое больше, переложить всё
   └── иначе            → split: две таблицы по старой ёмкости, делим по следующему биту хеша
                          (если localDepth == globalDepth — каталог удваивается)

каталог (globalDepth=2)
 00 ─┐
 01 ─┴─► table (localDepth=1)   несколько записей каталога могут указывать на одну таблицу
 10 ───► table (localDepth=2)
 11 ───► table (localDepth=2)
```

**Почему так.** В открытой адресации номер группы зависит от их числа, поэтому таблицу нельзя расширять по кусочку — только целиком. Чтобы «целиком» не значило «миллион элементов», таблица ограничена 1024 слотами (`maxTableCapacity`), а растёт каталог. Худший случай одного роста — переложить ≤ 1024 слота. Эвакуации и `oldbuckets` нет.

**Цена.** Большая карта = много мелких аллокаций: `make(map, 1<<20)` в замере ниже — **4097 allocs** против **20** у старой (каталог 2048 таблиц × (таблица + группы) + сам каталог). Итератор сложнее: при росте он продолжает идти по старой таблице и перепроверяет ключи в новой.

### 2.6 Итерация

Старт со случайных `dirOffset` и `entryOffset` (`table.go`), как и раньше — порядок не гарантирован. Правила спецификации те же: удалённый во время обхода ключ не вернётся, добавленный — может вернуться, может нет.

**Что важно для Senior**
- Главный выигрыш — проверка 8 слотов одной операцией и отсутствие overflow-указателей (меньше промахов кэша).
- Рост ограничен таблицей в 1024 слота — латентность вставки предсказуема без инкрементальной эвакуации.
- Tombstone — цена открытой адресации; карта с частыми insert/delete растёт не только от числа элементов.
- Маленькие локальные карты (≤ 8) могут вообще не аллоцироваться.

## 3. Сравнение и замеры

| | Старая (≤1.23, до 1.25 через флаг) | Swiss (1.24+) |
|---|---|---|
| Единица хранения | бакет: 8 пар + tophash + overflow ptr | группа: 8 слотов + control word |
| Выбор места | младшие `B` бит хеша | старшие биты → таблица, H1 → группа |
| Фильтр | tophash (8 бит), по байту | H2 (7 бит), все 8 сразу |
| Коллизии | цепочка overflow-бакетов | пробирование соседних групп |
| Удаление | `emptyOne` / `emptyRest` | пусто или tombstone |
| Load factor | 6.5/8 ≈ 81% | 7/8 = 87.5% |
| Рост | удвоение всего массива, эвакуация по кусочку | рост/сплит одной таблицы ≤ 1024 слотов |
| Маленькая карта | бакет в куче (или на стеке при `hint ≤ 8` и без escape) | одна группа, без таблицы |
| Уменьшение | нет | нет |

Бенчмарк (`map[int64]int64`, 1 048 576 ключей; одиночный прогон, M3 Pro):

```go
func BenchmarkLookupMiss(b *testing.B) {
	m := fill(n) // n = 1<<20
	for i := 0; b.Loop(); i++ {
		sink += m[int64(n+i)]
	}
}
```

Что следует: сильнее всего выигрывают **промахи** (пустой слот в группе виден сразу) и **вставка без hint**. Разброс 1.25-swiss vs 1.27 на `RangeStr`/`Insert` — шум одиночного прогона на ноутбуке, не регрессия (для вывода нужен `-count=10` + `benchstat`). Честное сравнение old vs swiss — в одной версии 1.25.

## 4. Грабли, заблуждения, советы

**Грабли: конкурентная запись**

```go
cache := map[string]int{}
var wg sync.WaitGroup
for w := range 4 {
	wg.Go(func() {
		for i := range 100000 {
			cache["sku:"+string(rune('a'+w))] = i
		}
	})
}
wg.Wait()
```

```text
$ go run .
fatal error: concurrent map writes

$ go run -race .
WARNING: DATA RACE
Write at 0x00c00019c000 by goroutine 6:
```

Почему: обе реализации ставят флаг записи (`hashWriting` / `Map.writing`, в swiss он переключается XOR, чтобы два писателя чаще замечали друг друга) — это best-effort детектор, не защита. Это `fatal error`: `recover` не поможет, процесс падает. `go vet` не ловит, ловит `-race`. Исправление: `sync.Mutex`/`RWMutex` вокруг карты, или `sync.Map` для «записали один раз — читаем много».

**Грабли: карта не уменьшается.** 1M элементов → `delete` всех → 36.0 MiB остаются (замер выше; так же было в старой: 38.2 MiB). Для кэша с вытеснением: периодически пересоздавать карту (`m = make(map[K]V, len(m))` с копированием живых) — после пика нагрузки. Не нужно, если размер карты стабилен. `clear(m)` память тоже не отдаёт.

| Заблуждение | На самом деле |
|---|---|
| «Swiss map — это SIMD, значит везде SIMD» | SIMD-интринсик только на amd64; на arm64 и др. — SWAR на `uint64` (`group.go`) |
| «В map есть overflow-бакеты, поэтому плохой хеш даёт длинные цепочки» | Верно до 1.23. С 1.24 цепочек нет — пробирование по группам |
| «Рост map — инкрементальная эвакуация» | Верно для старой. В swiss эвакуации нет: растёт одна таблица ≤ 1024 слотов целиком |
| «Можно вернуть старую map через `GOEXPERIMENT=noswissmap`» | Только в 1.24–1.25. В 1.26 флаг удалён |
| «Порядок обхода стабилен, если карту не менять» | Нет: случайный старт на каждом `range`, в обеих реализациях |

> **Совет.** Передавайте размер в `make(map[K]V, n)`, когда он известен заранее (загрузка справочника из PostgreSQL, батч из Kafka). Эффект в замере 1.27: 53.9 → 35.7 ms и 75.7 → 37.8 MB на 1M ключей. Не нужно для маленьких карт (≤ 8) и когда размер неизвестен — завышенный hint тратит память.

> **Совет.** Ключи и значения больше 128 байт (`MapMaxKeyBytes`/`MapMaxElemBytes`) хранятся по указателю — лишняя аллокация на элемент. Для крупных структур храните `map[K]*V` осознанно или уменьшите структуру. Не важно, если элементов мало.

**Что важно для Senior**
- Конкурентная запись — `fatal error`, ловится `-race`, не `go vet`.
- Карта не отдаёт память после удалений ни в старой, ни в новой реализации.
- `make` с hint — самая дешёвая оптимизация.

## 5. Вопросы для собеседования

1. 🟢 **Почему порядок `range` по map случайный?** Чтобы никто не полагался на порядок: старт итерации берётся из `rand()` при каждом обходе.
2. 🟢 **Что будет при записи в map из двух горутин?** `fatal error: concurrent map writes` (не panic, `recover` не ловит), если детектор сработал; иначе — порча данных. Ловит `-race`.
3. 🟢 **Почему нельзя взять адрес `&m[k]`?** При росте элементы перемещаются (в обеих реализациях) — указатель стал бы висячим.
4. 🟡 **Как устроен бакет старой map?** tophash[8], 8 ключей, 8 значений, указатель на overflow. Ключи и значения раздельно — без padding.
5. 🟡 **Когда старая map росла?** `count > 6.5·2^B` → удвоение; много overflow-бакетов → рост того же размера.
6. 🟡 **Что такое control word и H2?** 8 байт на группу, байт на слот; занятый слот хранит 7 младших бит хеша. Позволяет одним сравнением отсеять 8 слотов.
7. 🟡 **Зачем tombstone?** Поиск останавливается на группе с пустым слотом; пустая метка в полной группе оборвала бы поиск ключа, лежащего дальше.
8. 🟡 ⚠️ **Уменьшается ли map после `delete`?** Нет, ни в одной реализации. Пересоздать вручную.
9. 🔴 **Зачем swiss map делит карту на таблицы?** Открытую адресацию нельзя расширять по кусочку; таблицы ≤ 1024 слотов ограничивают худший случай одной вставки без эвакуации.
10. 🔴 **Что такое extendible hashing в map?** Каталог индексируется старшими `globalDepth` битами хеша; таблица с `localDepth < globalDepth` занимает несколько ячеек каталога; при сплите такой таблицы каталог не растёт.
11. 🔴 **Почему в swiss нет перестановки «на месте» для очистки tombstone?** Она ломает гарантии итерации; вместо этого — `pruneTombstones` (1.25+) или рост.
12. 🔴 ⚠️ **Swiss map везде использует SIMD?** Нет, интринсик только на amd64.
