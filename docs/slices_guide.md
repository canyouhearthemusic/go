# Срезы в Go: всё, что нужно знать на практике

Поведение проверено запуском на Go 1.26.1. Внутреннее устройство — заголовок, `growslice`, size classes — в [Slice.md](Slice.md).

## 1. Создание

```go
var s []int              // nil, len=0, cap=0, аллокаций нет
s := []int{}             // не nil, len=0, cap=0, но аллокация есть
s := []int{1, 2, 3}      // len=3, cap=3
s := make([]int, 5)      // пять нулей
s := make([]int, 0, 100) // len=0, cap=100 — под 100 элементов уже выделено
s := arr[:]              // срез на существующий массив, памяти не выделяет
s := slices.Repeat([]int{0}, 5)
```

`make([]T, len, cap)` — `len` обязателен, `cap` нет. `cap < len` — паника, отрицательный `len` — паника.

## 2. nil-срез и пустой срез

Разница есть, но она меньше, чем кажется.

| Операция | `var s []int` (nil) | `s := []int{}` |
|---|---|---|
| `len`, `cap` | 0, 0 | 0, 0 |
| `s == nil` | `true` | `false` |
| `append(s, 1)` | работает | работает |
| `copy(dst, s)` | работает, вернёт 0 | работает |
| `for range s` | 0 итераций | 0 итераций |
| `s[0]` | паника | паника |
| `s[0:0]` | валидно, даёт nil | валидно |
| `fmt.Println(s)` | `[]` | `[]` |
| `json.Marshal(s)` | `null` | `[]` |
| `slices.Equal(a, b)` | `true` для пары nil/пустой | |
| `reflect.DeepEqual(a, b)` | `false` для пары nil/пустой | |

Отсюда правила:

- **По умолчанию используй nil-срез.** Он не аллоцирует и ведёт себя как пустой во всех операциях.
- **Никогда не проверяй пустоту через `== nil`.** Только `len(s) == 0` — иначе пустой-но-не-nil срез пройдёт мимо.
- **Исключение — JSON.** Если API не должен отдавать `null`, инициализируй явно: `out := []Item{}`.

Контраст с картами: в nil-карту писать нельзя (паника), а в nil-срез — можно, `append` сам выделит память.

## 3. Общий backing array — источник большинства багов

Срез не владеет памятью единолично. Три ловушки, все связаны с этим.

### 3.1. Запись через один срез видна через другой

```go
a := []int{1, 2, 3, 4}
b := a[1:3]
b[0] = 99
// a == [1 99 3 4]
```

### 3.2. `append` может перетереть соседа — а может и не перетереть

```go
a := []int{1, 2, 3, 4}
b := a[:2]          // len=2, но cap=4 — тянется до конца a
b = append(b, 99)   // место есть → пишем НА МЕСТЕ
// a == [1 2 99 4]  ← append испортил a[2]
```

А если ёмкость кончилась — `growslice` выделит новый массив, и `a` останется нетронутым. Одна и та же строчка кода ведёт себя по-разному в зависимости от `cap`. Это худший вид бага: он проявляется на определённых размерах данных.

### 3.3. Защита — третий индекс

```go
b := a[:2:2]        // low:high:max → cap = max-low = 2
b = append(b, 99)   // места нет → новый массив, a цел
```

**Правило:** если отдаёшь подсрез наружу (в другую функцию, в структуру, в канал), ограничивай ёмкость: `a[i:j:j]`. Либо копируй: `slices.Clone(a[i:j])`.

Тот же приём нужен, когда хранишь «хвост» буфера: `rest := buf[n:len(buf):len(buf)]`.

### 3.4. Мусор за `len`

```go
e := []int{1, 2, 3, 4, 5}
f := e[:2]
fmt.Println(f[:cap(f)])   // [1 2 3 4 5] — видно всё
```

Ёмкость — это окно в чужие данные. Для буферов с чувствительным содержимым это утечка.

## 4. `append` возвращает новый заголовок

```go
append(s, x)       // результат потерян
s = append(s, x)   // правильно
```

`append` может вернуть другой `array`, и почти всегда возвращает другой `len`. Старая переменная об этом не узнает.

Отсюда же — почему функция не может «дописать» в срез вызывающего:

```go
func add(s []int) { s = append(s, 1) }   // ничего не меняет у вызывающего

s := make([]int, 0, 10)
add(s)
len(s)   // 0
```

Заголовок передан **по значению**. Меняй `s[i]` — это видно снаружи; меняй `len` — нет. Если нужно менять длину, возвращай срез (`s = add(s)`) или передавай `*[]int`.

## 5. Итерация

```go
for i, v := range s { ... }
```

- **`v` — копия элемента.** Изменение `v` не трогает срез. Для структур меняй через `s[i].Field = x` (элементы среза, в отличие от значений карты, адресуемы).
- **Длина вычисляется один раз, до начала цикла.** `append` внутри цикла не удлиняет обход:
  ```go
  k := []int{1, 2, 3}
  for range k { k = append(k, 0) }   // ровно 3 итерации, len(k) == 6
  ```
- **Удаление во время обхода по индексу** сдвигает элементы и пропускает соседний. Либо иди с конца, либо фильтруй в новый срез, либо `slices.DeleteFunc`.
- **Переменная цикла с Go 1.22 своя на каждой итерации**, поэтому `&v` даёт разные указатели. В коде под старые версии это была классическая ошибка.
- **`range` по массиву копирует массив**, если это не указатель и не срез: `for i, v := range arr` работает с копией `arr`. `range arr[:]` или `range &arr` — без копии.
- Нужен только индекс — `for i := range s`. Нужны только значения — `for _, v := range s`. Нужно N раз — `for i := range n` (Go 1.22+).
- `for v := range slices.Values(s)` и `slices.All(s)` — итераторы из Go 1.23, полезны при композиции с `iter`.

## 6. Рост и предварительная аллокация

Ёмкость удваивается до 256 элементов, дальше растёт примерно на 25% (детали и точные числа — в [Slice.md](Slice.md)). Каждый рост — это аллокация плюс копирование всего содержимого.

Что это стоит на 10 000 `append` (`int`, Apple M3 Pro):

```
без преаллокации   40197 ns/op   357625 B/op   19 allocs/op
make(..., 0, N)    22364 ns/op    81920 B/op    1 allocs/op
make(..., N) + [i]   6201 ns/op    81920 B/op    1 allocs/op
```

19 аллокаций вместо одной и в 4.4 раза больше суммарно выделенной памяти — это плата за неизвестный заранее размер.

- Знаешь размер — `make([]T, 0, n)` и `append`, либо `make([]T, n)` и запись по индексу (в измерении выше — ещё в 3.6 раза быстрее: на каждом элементе нет ни проверки ёмкости, ни обновления длины).
- Знаешь размер приблизительно — всё равно преаллоцируй: лишняя ёмкость дешевле цепочки реаллокаций.
- Добавляешь к уже существующему — `s = slices.Grow(s, n)` резервирует место под `n` **дополнительных** элементов.
- Держишь долго срез с огромным запасом — `s = slices.Clip(s)` обрезает `cap` до `len` (через копирование).

## 7. Удаление элементов

```go
// порядок важен
s = slices.Delete(s, i, i+1)        // сдвигает хвост, O(n)
s = append(s[:i], s[i+1:]...)       // то же самое руками

// порядок не важен — O(1)
s[i] = s[len(s)-1]
s = s[:len(s)-1]

// по условию
s = slices.DeleteFunc(s, func(x T) bool { return ... })
```

`slices.Delete` и `DeleteFunc` с Go 1.22 **зануляют освободившийся хвост** — это важно для срезов с указателями (см. следующий раздел). Ручной вариант через `append` этого не делает.

Удаление не уменьшает `cap`: память под массив остаётся выделенной.

## 8. Две разные утечки памяти

### 8.1. Подсрез держит весь массив

```go
func first10(data []byte) []byte {
    return data[:10]        // держит живым весь data, хоть мегабайт
}
```

GC освобождает объект целиком или не освобождает вовсе. Если от гигантского буфера нужен кусочек, который переживёт буфер, — копируй: `slices.Clone(data[:10])` или `bytes.Clone`.

### 8.2. Хвост за `len` держит указатели

Сборщик сканирует весь выделенный объект, а не первые `len` элементов:

```go
s := make([]*Conn, 3)   // три объекта
s = s[:1]               // "удалили" два
runtime.GC()            // освобождено: 0 из 2 — они всё ещё достижимы
```

Поэтому при укорачивании среза **указателей** (или структур с указателями, строками, срезами внутри) зануляй хвост:

```go
clear(s[1:])
s = s[:1]
```

Либо пользуйся `slices.Delete`, который делает это сам. Для срезов чисел и `struct{int,int}` проблемы нет — там нечего удерживать.

## 9. Копирование

```go
n := copy(dst, src)        // копирует min(len(dst), len(src)), возвращает сколько
copy(b, "строка")          // разрешённый частный случай
dst := slices.Clone(src)   // новый массив той же длины
dst := append([]T(nil), src...)   // то же самое до Go 1.21
```

- `copy` **не растит** приёмник. `copy(make([]int, 0), src)` скопирует ноль элементов — частая ошибка.
- `copy` безопасен при перекрытии внутри одного массива (внутри — `memmove`): `copy(s[1:], s[:4])` сдвигает вправо корректно.
- `slices.Clone` и любое копирование среза **поверхностные**: `[][]int`, `[]*T`, `[]map[...]` копируются вместе с общими внутренностями.
  ```go
  src := [][]int{{1, 2}}
  cl := slices.Clone(src)
  cl[0][0] = 999
  // src == [[999 2]]
  ```

## 10. Сравнение

Срезы **не сравнимы** оператором `==` — только с `nil`. Поэтому срез нельзя использовать как ключ карты и нельзя сравнить структуру, содержащую срез.

```go
slices.Equal(a, b)                  // поэлементно, для comparable
slices.EqualFunc(a, b, eq)          // со своим предикатом
bytes.Equal(a, b)                   // для []byte, быстрее
reflect.DeepEqual(a, b)             // медленно, различает nil и пустой
```

Если нужен срез в качестве ключа карты — приводи к строке: `m[string(b)]` для `[]byte` (компилятор делает это без аллокации), или собирай ключ-структуру из фиксированных полей.

## 11. Строки и `[]byte`

```go
b := []byte(s)     // копия, аллокация
s := string(b)     // копия, аллокация
```

Компилятор умеет обходиться без копии в нескольких конкретных случаях:

```go
m[string(b)]                    // ключ карты          — 0 аллокаций
if string(b) == "literal"       // сравнение           — 0 аллокаций
for i, r := range string(b)     // обход               — 0 аллокаций
switch string(b) { ... }        // выбор               — 0 аллокаций
```

Измеренная разница на поиске в карте: 5.8 ns/op и 0 аллокаций против 15.3 ns/op и 1 аллокации, если сохранить `string(b)` в переменную.

Для крайних случаев есть `unsafe.String(unsafe.SliceData(b), len(b))` и `unsafe.Slice(unsafe.StringData(s), len(s))` — без копии, но байты после этого нельзя менять (строки в Go неизменяемы, и это предположение зашито в компилятор и рантайм).

Сборка строк: `strings.Builder` (он же внутри держит `[]byte` и умеет отдавать строку без копии), для байтов — `bytes.Buffer` или просто `append`.

## 12. Пакет `slices`

| Функция | Что делает |
|---|---|
| `Clone`, `Equal`, `Contains`, `Index`, `IndexFunc` | базовые операции |
| `Sort`, `SortFunc`, `SortStableFunc`, `IsSorted` | сортировка без рефлексии (быстрее `sort.Slice`) |
| `BinarySearch`, `BinarySearchFunc` | поиск в отсортированном |
| `Delete`, `DeleteFunc`, `Insert`, `Replace` | изменение с сохранением порядка |
| `Compact`, `CompactFunc` | убрать соседние дубликаты |
| `Grow`, `Clip` | управление ёмкостью |
| `Reverse`, `Concat`, `Repeat` | прочее |
| `Min`, `Max`, `MinFunc`, `MaxFunc` | экстремумы |
| `All`, `Values`, `Backward`, `Collect`, `Sorted`, `AppendSeq`, `Chunk` | итераторы (1.23+) |

`slices.SortFunc(s, func(a, b T) int { ... })` принимает компаратор в стиле `cmp.Compare` (-1/0/+1), а не `less`. Для чисел и строк есть готовый `cmp.Compare`.

## 13. Многомерные срезы

```go
// наивно: n+1 аллокаций, строки разбросаны по памяти
grid := make([][]int, n)
for i := range grid { grid[i] = make([]int, m) }

// одна аллокация, данные подряд — заметно быстрее на обходе
flat := make([]int, n*m)
grid := make([][]int, n)
for i := range grid { grid[i] = flat[i*m : (i+1)*m : (i+1)*m] }
```

Либо вообще не заводи `[][]T`, а работай с плоским срезом и индексом `i*m + j`.

## 14. Производительность: мелочи, которые заметны

- Передача среза в функцию — 24 байта, независимо от длины. Указатель на срез (`*[]T`) нужен только чтобы менять длину, для скорости — нет.
- Проверка границ снимается компилятором, если он может доказать безопасность. `for i := range s { s[i] ... }` — без проверок. При ручном цикле помогает подсказка `s = s[:n]` или `_ = s[n-1]` перед циклом.
- `clear(s)` компилируется в `memclr`, это быстрее цикла присваиваний.
- `append(dst, src...)` — один `memmove`, а не цикл. Не разворачивай его руками.
- Срез структур (`[]T`) против среза указателей (`[]*T`): первый лучше для локальности и не грузит GC, второй — когда элементы большие и часто перемещаются между контейнерами.
- `make([]T, n)` с небольшим константным `n` у не убегающего среза попадает на стек — нулевая стоимость аллокации. Проверять через `go build -gcflags=-m`.

## 15. Шпаргалка ошибок

| Симптом | Причина |
|---|---|
| Изменения не видны после вызова функции | функция сделала `s = append(...)`, заголовок передан по значению |
| Чужой срез внезапно изменился | общий backing array; ограничь `a[i:j:j]` или копируй |
| `index out of range [N] with length M` | индексация за `len` |
| `slice bounds out of range [:N] with capacity M` | слайсинг за `cap` |
| Данные то портятся, то нет | `append` на месте против `append` с реаллокацией — зависит от `cap` |
| Память не освобождается | подсрез держит большой массив, либо хвост за `len` держит указатели |
| `null` вместо `[]` в JSON | nil-срез; инициализируй `[]T{}` |
| Цикл `range` не видит добавленное | длина зафиксирована до начала цикла |
| Изменения в `for _, v := range` пропадают | `v` — копия, пиши через `s[i]` |
| `slices.Clone` не защитил от изменений | копия поверхностная, внутренние срезы/карты общие |
| Неожиданный `cap` после `append` | округление до size class, к арифметике не сводится |
