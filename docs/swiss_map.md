Актуально для Go 1.24+ (реализация проверена по дереву go1.25.11).

Это разбор внутреннего устройства. Практическая сторона — nil-карты, ключи, итерация, конкурентность, паттерны — в [maps_guide.md](maps_guide.md).

Swiss table — реализация `map` по умолчанию начиная с Go 1.24. Старая реализация с бакетами и overflow-цепочками осталась в дереве и включается через `GOEXPERIMENT=noswissmap` (флаг `goexperiment.SwissMap`, см. `src/internal/goexperiment/flags.go:115`). Код: `src/internal/runtime/maps/`.

## Терминология

- **Слот (Slot):** место хранения одной пары ключ/элемент.
- **Группа (Group):** группа из `abi.SwissMapGroupSlots` (8) слотов плюс управляющее слово.
- **Управляющее слово (Control word):** 8-байтовое слово, которое указывает, является ли каждый слот пустым, удалённым или используемым. Если слот используется, его управляющий байт также содержит младшие 7 бит хеша (H2).
- **H1:** старшие биты хеша (на 64-битных платформах — верхние 57 бит; на 32-битных — верхние 25). Используется для выбора стартовой группы.
- **H2:** младшие 7 бит хеша. Хранится в управляющем байте.
- **Таблица (Table):** полная хеш-таблица «Swiss Table». Таблица состоит из одной или нескольких групп для хранения плюс метаданных для управления работой и определения момента роста.
- **Карта (Map):** тип верхнего уровня `Map` состоит из нуля или более таблиц для хранения. Верхние биты хеша выбирают, какой таблице принадлежит ключ.
- **Каталог (Directory):** массив таблиц, используемых картой.

По своей сути дизайн таблицы похож на традиционную хеш-таблицу с открытой адресацией. Хранилище состоит из массива групп, что фактически означает массив слотов ключ/элемент с разбросанными между ними управляющими словами. Поиск использует хеш для определения начальной группы для проверки. Если из-за коллизий эта группа не содержит совпадения, последовательность проб выбирает следующую группу для проверки (подробнее о последовательности проб см. ниже).

**Overflow-бакетов нет.** Это ключевое отличие от старой реализации: заполненная группа не порождает отдельную аллокацию, подвешенную по указателю. Пробирование просто переходит к следующей группе того же плоского массива. Конец «цепочки» помечается не nil-указателем, а наличием пустого слота в группе.

Ключевое различие проявляется внутри группы. В стандартной хеш-таблице с открытой адресацией и линейным пробированием мы бы проверяли каждый слот по одному, чтобы найти совпадение. Swiss table использует дополнительное управляющее слово для параллельной проверки всех 8 слотов.

## Управляющее слово (control word)

### Что это

Группа — это 8 слотов для пар ключ/значение плюс 8 байт метаданных. Эти 8 байт и есть control word.

```
group:
  [8 байт метаданных] [слот 0] [слот 1] ... [слот 7]
   ^^^^^^^^^^^^^^^^^^
   control word
```

Один байт метаданных описывает один слот. Байт №3 описывает слот №3.

8 байт = один `uint64`. Процессор читает его одной командой.

### Что в байте

Байт хранит две вещи сразу:

- **состояние слота**: пуст / удалён / занят;
- если занят — **7 младших бит хеша** ключа, который в этом слоте лежит. Это называется H2.

```
1 0000000  — пусто
1 1111111  — удалён (tombstone)
0 xxxxxxx  — занят, xxxxxxx это H2
```

Старший бит: 1 = в слоте нет данных, 0 = есть данные.

### Зачем H2 в метаданных

Поиск ключа требует сравнить ключ с тем, что лежит в слоте. Ключ может быть строкой, структурой, чем угодно большим — сравнение дорогое, плюс нужно лезть в память за самим слотом.

H2 — это 7 бит хеша, скопированные в метаданные. Их можно сравнить, не трогая слот вообще.

Поиск работает так: посчитали хеш ключа, взяли из него те же 7 бит, сравнили со всеми 8 байтами control word. Совпало у слотов 0 и 3 — значит остальные 6 слотов точно не наши, читать их не надо. Читаем только слоты 0 и 3 и сравниваем ключи по-настоящему.

7 бит — это 128 вариантов. Разные ключи могут дать одинаковые 7 бит. Поэтому H2 не доказывает совпадение, а только отсеивает заведомо не подходящее. Полная сверка ключа через `typ.Key.Equal` обязательна всегда.

### Три операции

Все три сравнивают весь control word целиком, одной операцией на все 8 слотов сразу. Возвращают набор номеров слотов (`bitset`).

**`matchH2(h2)`** — какие слоты заняты и имеют такой H2. Это кандидаты на совпадение.

**`matchEmpty()`** — какие слоты пусты. Пустой слот означает, что поиск можно прекращать: если бы ключ существовал, он лежал бы здесь или раньше. Удалённые слоты сюда не попадают — через них поиск продолжается.

**`matchEmptyOrDeleted()`** — какие слоты свободны под запись. Это просто проверка старшего бита у всех восьми.

Есть ещё `matchFull()` — какие слоты заняты; используется в `pruneTombstones`.

### Почему кодировка именно такая

Она подобрана под эти операции.

Занят или нет — старший бит. Одна проверка одного бита, потому что это самый частый вопрос.

Пусто и удалено оба имеют старший бит 1, но различаются битом №1 (`0000000` против `1111111`). Поэтому «пусто, но не удалено» — тоже одна битовая операция, а не два сравнения.

H2 занимает ровно оставшиеся 7 бит, впритык, без отдельного поля.

### Почему слотов ровно 8

Потому что 8 байт помещаются в `uint64`, и все операции над control word — это арифметика над одним машинным словом.

На amd64 эти операции компилятор заменяет на SIMD-инструкции. SIMD мог бы обрабатывать 16 байт, то есть 16 слотов, но тогда портируемая версия на других архитектурах перестала бы работать через `uint64`. Выбрали 8 — общий знаменатель.

### Что это даёт

Поиск в группе — это одно чтение 8 байт метаданных плюс обычно одно чтение слота. Вместо восьми чтений слотов. Метаданные лежат вплотную к слотам и попадают в кеш вместе с ними, так что первое чтение почти бесплатное.

### SWAR и SIMD

Портируемая реализация `match*` — это SWAR-трюки над `uint64` (см. `ctrlGroupMatchH2` в `group.go:157`). **На AMD64 эти функции заменяются компиляторными интринсиками на SIMD-инструкциях**, и представление `bitset` при этом другое:

- на AMD64 — упакованный битсет: 1 бит на слот, `first()` — просто `TrailingZeros64`;
- на остальных архитектурах — 1 **байт** на слот (`0x80` = входит в множество), `first()` = `TrailingZeros64 >> 3`.

Поэтому код никогда не интерпретирует `bitset` напрямую, только через `first()`/`removeFirst()`.

У портируемого `matchH2` есть известные ложные срабатывания на определённых комбинациях байтов (см. комментарий в `group.go:161-167`) — на корректность не влияет, так как сверка ключа обязательна в любом случае.

## Коэффициент загрузки и ёмкость

- `maxAvgGroupLoad = 7` (`group.go:20`) — таблица растёт, когда занято 7/8 слотов. Именно это гарантирует, что **в таблице всегда есть хотя бы один пустой слот**, — на этом инварианте держится вся логика останова пробирования.
- Таблица из одной группы — особый случай: заполняется `capacity - 1` слотов, то есть 7 из 8 (`table.maxGrowthLeft`, `table.go:116-135`).
- `maxTableCapacity = 1024` (`table.go:20`) — предел ёмкости одной таблицы. Дальше таблица расщепляется, а не растёт. Это ограничивает максимальную латентность одного роста.
- `growthLeft` считает вниз оставшиеся вставки: `used + tombstones > loadFactor*capacity` → rehash. Tombstone учитываются, чтобы таблица не переполнилась ими.

## Пробирование

Пробирование выполняется с использованием H1 (старших бит хеша) в качестве индекса в массиве групп. Пробирование проходит через группы, используя квадратичное пробирование, пока не найдёт группу с совпадением или группу с пустым слотом. Подробности о последовательности проб см. в `probeSeq`. Обратите внимание на инварианты пробирования: количество групп должно быть степенью двойки, а конец последовательности проб должен быть группой с пустым слотом (таблица никогда не может быть заполнена на 100%).

Последовательность — треугольная прогрессия:

```
p(i) = (i² + i)/2 + H1  (mod количество_групп)
```

При количестве групп, равном степени двойки, `(i²+i)/2` — биекция в Z/2^m, поэтому последовательность обходит **каждую группу ровно один раз** и гарантированно завершается.

```go
func makeProbeSeq(hash uintptr, mask uint64) probeSeq {
	return probeSeq{mask: mask, offset: uint64(hash) & mask, index: 0}
}

func (s probeSeq) next() probeSeq {
	s.index++
	s.offset = (s.offset + s.index) & s.mask
	return s
}
```

## Удаление

Пробирование останавливается, когда находит группу с пустым слотом. Это влияет на удаление: при удалении из полностью заполненной группы мы не должны помечать слот как пустой, поскольку дальше в последовательности проб могут быть используемые слоты, и это удаление привело бы к слишком ранней остановке пробирования. Вместо этого мы помечаем такие слоты как «удалённые» надгробным маркером (tombstone). Если в группе ещё есть пустой слот, надгробный маркер не нужен, и мы напрямую помечаем слот как пустой и возвращаем `growthLeft++`. Вставка отдаёт приоритет повторному использованию надгробных маркеров перед заполнением пустых слотов.

Логика решения (`table.Delete`, `table.go:465-477`): «только полная группа может оказаться в середине последовательности проб; группа, ставшая полной, остаётся полной до rehash. Поэтому если группа не полна сейчас — можно просто освободить слот».

При удалении содержимое слота зачищается:
- **элемент** зачищается всегда, даже если не содержит указателей, — от этого зависят составные присваивания вроде `m[k] += x` (go.dev/issue/25936);
- **ключ** зачищается только если содержит указатели (иначе смысла нет — GC он не держит).

`Map.tombstonePossible` — глобальный флаг: `false`, если ни в одной таблице карты точно нет tombstone. Позволяет пропускать лишнюю работу в `Clear`.

### pruneTombstones

Надгробные маркеры убираются не только при росте. Когда `growthLeft` дошёл до нуля, перед ростом вызывается `table.pruneTombstones` (`table.go:494`), который пытается удалить ненужные маркеры **на месте**:

1. Если tombstone меньше 10% ёмкости — сразу выход (не окупится).
2. Иначе прослеживается probe sequence каждой заполненной записи, и каждая группа с tombstone, через которую эта последовательность проходит, помечается как «нужная».
3. Все непомеченные tombstone превращаются обратно в `ctrlEmpty`, `growthLeft` восстанавливается.

Ключи, не равные самим себе (NaN), пропускаются: их всё равно невозможно найти поиском, только итерацией, поэтому их цепочки можно рвать.

Смысл порога в 10%: pruning стоит O(n), поэтому он должен освобождать O(n) слотов. Иначе дешевле вырасти (тоже O(n), но гарантирует O(n) последующих вставок за константу).

Полноценный «rehash in place», который переупорядочивает слоты (как в Abseil), **не** реализован — он ломает семантику итерации, поскольку итератор просто идёт по слотам по порядку. См. TODO в `table.rehash`.

Важная асимметрия в текущем дереве: `pruneTombstones` вызывается из `table.PutSlot` (`table.go:330`) и из быстрых путей (`runtime_fast32_swiss.go:297`, `runtime_fast64_swiss.go:297`, `runtime_faststr_swiss.go:368`), но **не** из обобщённого `runtime_mapassign`.

## Рост

Последовательность проб зависит от количества групп. Поэтому при увеличении количества групп все слоты должны быть переупорядочены в соответствии с новой последовательностью проб. Другими словами, вся таблица должна расти за один раз.

Чтобы поддерживать инкрементальный рост, карта разделяет своё содержимое между несколькими таблицами. Каждая таблица по-прежнему является полной хеш-таблицей, но отдельная таблица может обслуживать только подмножество хеш-пространства. Рост происходит на отдельных таблицах, поэтому, хотя вся таблица должна расти за один раз, каждый из этих ростов составляет лишь небольшую часть карты. Максимальный размер одного роста ограничивается ограничением максимального размера таблицы до того, как она будет разделена на несколько таблиц.

Карта начинается с одной таблицы. Вплоть до `maxTableCapacity` (1024) рост просто заменяет эту таблицу заменой с удвоенной ёмкостью. За пределами этого лимита рост разделяет таблицу на две.

```go
func (t *table) rehash(typ *abi.SwissMapType, m *Map) {
	newCapacity := 2 * t.capacity
	if newCapacity <= maxTableCapacity {
		t.grow(typ, m, newCapacity)   // удвоение
		return
	}
	t.split(typ, m)                   // расщепление
}
```

Обе операции строят новую таблицу и переносят записи через `uncheckedPutSlot` (вставка без проверки на существование — при переносе дубликатов быть не может). Заодно это **полностью устраняет все tombstone**: перенос пропускает всё, у чего установлен бит `ctrlEmpty` (то есть и empty, и deleted). Старая таблица помечается `t.index = -1` («устаревшая») и отдаётся GC — но итератор может продолжать по ней ходить.

**Инкрементальности внутри одной таблицы нет.** В отличие от старой реализации с постепенной эвакуацией бакетов, здесь таблица переносится целиком за одну операцию вставки. Инкрементальность достигается на уровне карты: за раз растёт максимум 1024 записи.

Карта использует «расширяемое хеширование» (extendible hashing) для выбора используемой таблицы. При расширяемом хешировании мы используем верхние биты хеша в качестве индекса в массиве таблиц (называемом «каталогом»). Количество используемых бит увеличивается по мере увеличения количества таблиц. Например, когда есть только 1 таблица, мы используем 0 бит (выбор не нужен). Когда есть 2 таблицы, мы используем 1 бит для выбора 0-й или 1-й таблицы. `Map.globalDepth` — это количество бит, используемых в настоящее время для выбора таблицы, и, соответственно, `(1 << globalDepth)` — размер каталога.

Обратите внимание, что каждая таблица имеет свой собственный коэффициент загрузки и растёт независимо. Если 1-я таблица вырастет, она разделится. Нам понадобятся 2 бита для выбора таблиц, хотя у нас будет 3 таблицы всего, а не 4. Мы поддерживаем это, позволяя нескольким индексам указывать на одну и ту же таблицу. Этот пример:

```
каталог (globalDepth=2)
+----+
| 00 | --\
+----+    +--> таблица (localDepth=1)
| 01 | --/
+----+
| 10 | ------> таблица (localDepth=2)
+----+
| 11 | ------> таблица (localDepth=2)
+----+
```

Таблицы отслеживают глубину, на которой они были созданы (`localDepth`). Необходимо увеличивать каталог при разделении таблицы, где `globalDepth == localDepth`.

### Расщепление таблицы

`table.split` (`table.go:1152`) создаёт две таблицы `left` и `right` **сразу с максимальной ёмкостью** (`maxTableCapacity`) и `localDepth+1`, затем распределяет записи по биту `localDepth` от старшего края хеша:

```go
mask := localDepthMask(localDepth)   // 1 << (64 - localDepth)
if hash&mask == 0 { newTable = left } else { newTable = right }
```

`Map.installTableSplit` (`map.go:359`) ставит их в каталог. Если `old.localDepth == m.globalDepth`, места в каталоге нет — каталог **удваивается**: каждая существующая таблица дублируется в две соседние ячейки (`newDir[2*i] = newDir[2*i+1] = t`), `globalDepth++`, `globalShift--`. Каталог хранит указатели, поэтому его удвоение дёшево относительно переноса данных.

## Малые карты (small map optimization)

Если карта никогда не содержала больше 8 записей, она **целиком помещается в одну группу** и живёт без каталога, без таблицы и без пробирования: `dirLen == 0`, `dirPtr` указывает прямо на группу.

- `growToSmall` — первая вставка: аллоцируется одна группа.
- `putSlotSmall` / `getWithKeySmall` — один `matchH2` по 8 слотам и всё; **проверка на empty при поиске не нужна** (одна группа = искать больше негде).
- Малые карты **никогда не содержат tombstone**: probe sequence нет, поэтому удаление всегда ставит `ctrlEmpty`. Поэтому же малая карта может занять все 8 слотов, а не 7.
- 9-я запись → `growToTable`: создаётся полноценная таблица на `2*SwissMapGroupSlots` = 16 слотов, все записи перехешируются, создаётся каталог из одной таблицы, `globalDepth = 0`.
- Компилятор может выделить группу для малой карты **на стеке** — тогда `m.dirPtr` уже инициализирован при входе в `NewMap` (см. комментарий в `NewMap`).
- `make(map[K]V, hint)` при `hint <= 8` вообще ничего не аллоцирует — аллокация откладывается до первой записи.

Это очень частый случай на практике, и именно он даёт основной выигрыш swiss map на маленьких картах.

## Предварительный сайзинг

`NewMap` с `hint > 8` считает ёмкость под нужное число записей *с учётом* коэффициента загрузки:

```go
targetCapacity := (hint * abi.SwissMapGroupSlots) / maxAvgGroupLoad  // hint * 8/7
dirSize := (targetCapacity + maxTableCapacity - 1) / maxTableCapacity
dirSize, _ = alignUpPow2(dirSize)
```

и сразу создаёт каталог из `dirSize` таблиц. То есть `make(map[K]V, n)` действительно избавляет от роста при вставке `n` элементов. При переполнении любых вычислений возвращается пустая карта (рост произойдёт естественным образом).

## Раскладка памяти

```go
type group struct {
	ctrls ctrlGroup                    // 8 байт: по байту на слот
	slots [abi.SwissMapGroupSlots]slot
}

type slot struct {
	key  typ.Key
	elem typ.Elem
}
```

Ключи и элементы **чередуются** в пределах слота — это максимизирует локальность при попадании (ключ и значение на одной кеш-линии), но тратит место на паддинг для типов вроде `map[uint8]uint64`. В коде на это есть TODO.

Группы лежат в одном плоском массиве (`newarray(typ.Group, length)`), доступ — `data + i*GroupSize`, индекс маскируется `lengthMask` (степень двойки).

**Indirect key/elem:** если ключ или значение больше 128 байт (`SwissMapMaxKeyBytes` / `SwissMapMaxElemBytes`), в слоте хранится **указатель**, а сами данные аллоцируются отдельно. Отсюда всюду в коде проверки `typ.IndirectKey()` / `typ.IndirectElem()`.

Флаги типа (`abi.SwissMapType.Flags`):

| Флаг | Значение |
|---|---|
| `SwissMapNeedKeyUpdate` | ключ надо перезаписывать при обновлении (например, `-0.0` → `+0.0` для float) |
| `SwissMapHashMightPanic` | хеш-функция может запаниковать (интерфейсный ключ с несравнимым динамическим типом) |
| `SwissMapIndirectKey` | ключ хранится по указателю |
| `SwissMapIndirectElem` | значение хранится по указателю |

## Быстрые пути

Для распространённых типов ключей компилятор генерирует вызовы специализированных функций, минуя обобщённые: `runtime_fast32_swiss.go`, `runtime_fast64_swiss.go`, `runtime_faststr_swiss.go` (`mapaccess1_fast64`, `mapassign_fast64`, `mapdelete_faststr` и т. д.). В них зашиты прямые сравнения ключей вместо вызова `typ.Key.Equal` через указатель, а для строк — быстрая проверка длины и указателя до полного сравнения.

## Детект конкурентного доступа

`Map.writing` — флаг, который **переключается** (`^= 1`), а не устанавливается. Причина в комментарии к полю: при нескольких конкурентных писателях переключение повышает вероятность, что гонку заметят обе стороны.

- Чтение при `writing != 0` → `fatal("concurrent map read and map write")`.
- Запись при `writing != 0` → `fatal("concurrent map writes")`.
- В конце операции проверяется, что флаг всё ещё установлен: если нет — тоже фатальная ошибка.
- Флаг ставится **после** вызова `Hasher`, потому что хеш может запаниковать (несравнимый ключ, `HashMightPanic`), и тогда записи фактически не было.

Это best-effort детектор, а не гарантия. Полноценно гонки на картах ловит только `-race`.

## Clear

`Map.Clear` не освобождает память — таблицы обнуляются на месте (`t.Clear` → `reset` управляющих слов и `typedmemclr` слотов), каталог сохраняется (`TODO: shrink directory?`). Дополнительно:

- `m.clearSeq++` — счётчик очисток, по нему итератор понимает, что карту очистили под ним;
- `m.seed = uintptr(rand())` — **сид хеша переустанавливается**, чтобы затруднить атакующему повторное воспроизведение коллизий (go.dev/issue/25237);
- `m.tombstonePossible = false`.

## Итерация

Итерация — самая сложная часть карты из-за щедрой семантики итерации в Go. Сводка семантики из спецификации:

1. Добавление и/или удаление записей во время итерации НЕ ДОЛЖНО приводить к тому, что итерация вернёт одну и ту же запись более одного раза.
2. Записи, добавленные во время итерации, МОГУТ быть возвращены итерацией.
3. Записи, изменённые во время итерации, ДОЛЖНЫ возвращать своё последнее значение.
4. Записи, удалённые во время итерации, НЕ ДОЛЖНЫ возвращаться итерацией.
5. Порядок итерации не определён. В реализации он явно рандомизирован.

Рандомизация — два случайных смещения, выбираемых в `Iter.Init`: `entryOffset` (стартовый слот внутри таблицы) и `dirOffset` (стартовый индекс каталога). Реальный индекс считается как `(it.dirIdx + it.dirOffset) & (dirLen-1)`. Для малых карт `dirIdx = -1` служит признаком, а слот выбирается как `(entryIdx + entryOffset) % 8`.

Если карта никогда не растёт, эта семантика проста: просто итерируем по каждой таблице в каталоге и по каждой группе и слоту в каждой таблице. Вся эта семантика срабатывает как ожидается.

Если карта растёт во время итерации, всё значительно усложняется. Прежде всего, нам нужно отслеживать, какие записи мы уже вернули, чтобы удовлетворить (1). Существует три типа роста:

- **а.** Таблица заменена одной более крупной таблицей.
- **б.** Таблица разделена на две заменяющие таблицы.
- **в.** Рост каталога (происходит как часть (б), если необходимо).

Для всех этих случаев заменяющая таблица(ы) будет иметь другую последовательность проб, поэтому простого отслеживания текущих индексов группы и слота недостаточно.

Для (а) и (б) обратите внимание, что рост таблиц, отличных от той, по которой мы в настоящее время итерируем, не имеет значения.

Мы обрабатываем (а) и (б), заставляя итератор сохранять ссылку на таблицу, по которой он в настоящее время итерирует, даже после замены таблицы. Мы продолжаем итерировать по исходной таблице, чтобы сохранить порядок итерации и избежать нарушения (1). Любые новые записи, добавленные только в заменяющую таблицу(ы), будут пропущены (разрешено (2)). Чтобы избежать нарушения (3) или (4), хотя мы используем исходную таблицу для выбора ключей, мы должны искать их снова в новой таблице(ах), чтобы определить, были ли они изменены или удалены. Существует ещё один уровень сложности, если ключ не сравнивается равным самому себе. Жуткие подробности см. в `Iter.Next`.

Обратите внимание, что для (б) после завершения итерации по старой таблице нам нужно будет пропустить следующую запись в каталоге, поскольку она содержит вторую часть разделения старой таблицы. Мы можем использовать `localDepth` старой таблицы для определения следующего логического индекса: `entries := 1 << (globalDepth - tab.localDepth)`.

При росте каталога (в) нужно скорректировать текущий индекс каталога. Это более прямолинейно, поскольку порядок каталога остаётся прежним после роста, поэтому мы просто сдвигаем индекс на количество удвоений: `it.dirIdx <<= (m.globalDepth - it.globalDepth)`.

> Примечание: в комментарии в исходниках (`map.go:177`) этот абзац помечен как «For (b)», хотя речь про (c) — опечатка в апстриме.

## Ключевые определения из исходников

Извлечение частей хеша:

```go
// Extracts the H1 portion of a hash: the 57 upper bits.
// TODO(prattmic): what about 32-bit systems?
func h1(h uintptr) uintptr {
	return h >> 7
}

// Extracts the H2 portion of a hash: the 7 bits not used for h1.
//
// These are used as an occupied control byte.
func h2(h uintptr) uintptr {
	return h & 0x7f
}
```

Обратите внимание: **биты для выбора таблицы в каталоге и H1 пересекаются**. Каталог берёт верхние `globalDepth` бит, которые целиком лежат внутри H1. Непересекающихся частей у хеша только две: H1 и H2.

```go
// Note: changes here must be reflected in cmd/compile/internal/reflectdata/map_swiss.go:SwissMapType.
type Map struct {

	// The number of filled slots (i.e. the number of elements in all
	// tables). Excludes deleted slots.
	// Must be first (known by the compiler, for len() builtin).
	used uint64

	// seed is the hash seed, computed as a unique random number per map.
	seed uintptr

	// The directory of tables.
	//
	// Normally dirPtr points to an array of table pointers
	//
	// dirPtr *[dirLen]*table
	//
	// The length (dirLen) of this array is `1 << globalDepth`. Multiple
	// entries may point to the same table. See top-level comment for more
	// details.
	//
	// Small map optimization: if the map always contained
	// abi.SwissMapGroupSlots or fewer entries, it fits entirely in a
	// single group. In that case dirPtr points directly to a single group.
	//
	// dirPtr *group
	//
	// In this case, dirLen is 0. used counts the number of used slots in
	// the group. Note that small maps never have deleted slots (as there
	// is no probe sequence to maintain).
	dirPtr unsafe.Pointer
	dirLen int

	// The number of bits to use in table directory lookups.
	globalDepth uint8

	// The number of bits to shift out of the hash for directory lookups.
	// On 64-bit systems, this is 64 - globalDepth.
	globalShift uint8

	// writing is a flag that is toggled (XOR 1) while the map is being
	// written. Normally it is set to 1 when writing, but if there are
	// multiple concurrent writers, then toggling increases the probability
	// that both sides will detect the race.
	writing uint8

	// tombstonePossible is false if we know that no table in this map
	// contains a tombstone.
	tombstonePossible bool

	// clearSeq is a sequence counter of calls to Clear. It is used to
	// detect map clears during iteration.
	clearSeq uint64
}
```

```go
// table is a Swiss table hash table structure.
//
// Each table is a complete hash table implementation.
//
// Map uses one or more tables to store entries. Extendible hashing (hash
// prefix) is used to select the table to use for a specific key. Using
// multiple tables enables incremental growth by growing only one table at a
// time.
type table struct {

	// The number of filled slots (i.e. the number of elements in the table).
	used uint16

	// The total number of slots (always 2^N). Equal to
	// `(groups.lengthMask+1)*abi.SwissMapGroupSlots`.
	capacity uint16

	// The number of slots we can still fill without needing to rehash.
	//
	// We rehash when used + tombstones > loadFactor*capacity, including
	// tombstones so the table doesn't overfill with tombstones. This field
	// counts down remaining empty slots before the next rehash.
	growthLeft uint16

	// The number of bits used by directory lookups above this table. Note
	// that this may be less then globalDepth, if the directory has grown
	// but this table has not yet been split.
	localDepth uint8

	// Index of this table in the Map directory. This is the index of the
	// _first_ location in the directory. The table may occur in multiple
	// sequential indicies.
	//
	// index is -1 if the table is stale (no longer installed in the
	// directory).
	index int

	// groups is an array of slot groups. Each group holds abi.SwissMapGroupSlots
	// key/elem slots and their control bytes. A table has a fixed size
	// groups array. The table is replaced (in rehash) when more space is
	// required.
	//
	// TODO(prattmic): keys and elements are interleaved to maximize
	// locality, but it comes at the expense of wasted space for some types
	// (consider uint8 key, uint64 element). Consider placing all keys
	// together in these cases to save space.
	groups groupsReference
}
```

```go
// Each slot in the hash table has a control byte which can have one of three
// states: empty, deleted, and full. They have the following bit patterns:
//
// empty: 1 0 0 0 0 0 0 0
// deleted: 1 1 1 1 1 1 1 0
// full: 0 h h h h h h h // h represents the H2 hash bits
//
// TODO(prattmic): Consider inverting the top bit so that the zero value is empty.
type ctrl uint8

// ctrlGroup is a fixed size array of abi.SwissMapGroupSlots control bytes
// stored in a uint64.
type ctrlGroup uint64


// groupReference is a wrapper type representing a single slot group stored at
// data.
//
// A group holds abi.SwissMapGroupSlots slots (key/elem pairs) plus their
// control word.
type groupReference struct {

	// data points to the group, which is described by typ.Group and has
	// layout:
	//
	// type group struct {
	//    ctrls ctrlGroup
	//    slots [abi.SwissMapGroupSlots]slot
	// }
	//
	// type slot struct {
	//    key typ.Key
	//    elem typ.Elem
	// }
	data unsafe.Pointer // data *typ.Group
}

// groupsReference is a wrapper type describing an array of groups stored at
// data.
type groupsReference struct {

	// data points to an array of groups. See groupReference above for the
	// definition of group.
	data unsafe.Pointer // data *[length]typ.Group

	// lengthMask is the number of groups in data minus one (note that
	// length must be a power of two). This allows computing i%length
	// quickly using bitwise AND.
	lengthMask uint64
}
```

Заметьте кодировку `ctrl`: у empty и deleted старший бит установлен, у full — сброшен. Отсюда идиома `if (ctrl & ctrlEmpty) == ctrlEmpty { continue }` в `grow`/`split` — она за одну проверку отсеивает и пустые, и удалённые слоты.

# Map Access

![[swiss_map_lookup_detailed.svg|697]]

![[swiss_map_lookup_chain.svg|697]]

**0. Точка входа.** Выражение `v := m[k]` компилятор превращает в вызов `runtime.mapaccess1` (или специализированный вариант вроде `mapaccess1_fast64` для простых типов ключей; для формы `v, ok := m[k]` — `mapaccess2`). Дальше управление уходит в `internal/runtime/maps`, в `runtime_mapaccess1` (`runtime_swiss.go:40`), где цикл пробирования **встроен прямо в функцию**, а не вызывает `(*Map).Get`. Методы `Map.Get` / `Map.getWithKey` используются reflect-путями и итерацией.

**1. Хеш.** Считается один раз: `hash := typ.Hasher(key, m.seed)`. Из него выделяются две непересекающиеся части — `H1 = hash >> 7` (старшие биты) и `H2 = hash & 0x7f` (младшие 7 бит). Индекс каталога берётся из верхних бит, которые лежат внутри H1. Один хеш обслуживает все уровни.

Ранние выходы до всякого пробирования: `m == nil || m.Used() == 0` → возврат нулевого значения (но с проверкой `mapKeyError`, чтобы `m[nanKey]` на nil-карте всё равно паниковала там, где должна — issue 23734).

**2. Каталог → таблица.** Если карта маленькая (`dirLen == 0`), есть быстрый путь: `dirPtr` указывает прямо на группу, и уровни «каталог» и «таблица» схлопываются — `getWithKeySmall`. Иначе:

```go
func (m *Map) directoryIndex(hash uintptr) uintptr {
	if m.dirLen == 1 {
		return 0
	}
	return hash >> (m.globalShift & 63)
}
```

`globalShift = 64 - globalDepth` (на 32-битных — `32 - globalDepth`). Ранний выход при `dirLen == 1` обязателен: при `globalDepth == 0` сдвиг на 64 некорректен. Несколько индексов могут указывать на одну таблицу (ситуация с `localDepth < globalDepth`).

**3. Таблица → стартовая группа.** Внутри выбранной таблицы `H1` задаёт начало последовательности проб: `seq := makeProbeSeq(h1(hash), t.groups.lengthMask)`, где стартовое смещение — это `H1 & lengthMask` (количество групп — степень двойки, поэтому маска вместо деления).

**4. Группа → кандидаты.** Из группы читается 8-байтовое управляющее слово, и `matchH2(H2)` за одну операцию (SIMD на amd64, SWAR на прочих) сравнивает 7-битный `H2` сразу со всеми 8 контрольными байтами. На выходе — битовая маска слотов-кандидатов. Это и есть «8 шагов пробирования за раз».

**5. Слоты → элемент.** По каждому установленному биту маски делается _настоящее_ сравнение ключа (`H2` совпадает ложно примерно 1 раз из 128, поэтому проверка обязательна). Совпал — возвращается указатель на элемент.

**6. Развязки внутри группы.** Если совпадения в группе нет:

- встретился **пустой** слот (`matchEmpty != 0`) → ключа в карте нет, поиск останавливается (это инвариант: конец пробы — всегда группа с пустым слотом);
- группа **заполнена целиком** (включая tombstone-маркеры) → `seq.next()` уводит к следующей группе по квадратичному пробированию, и шаги 4–5 повторяются.

Ключевой момент всей конструкции: дорогая операция (доступ к памяти со сравнением ключей) выполняется только по кандидатам, которые отобрала дешёвая параллельная проверка `H2` в управляющем слове.

Ожидаемая стоимость промаха по `Key.Equal` (из комментария к `getWithKey`): при k «неправильных» объектов в последовательности проб ожидаемое число совпадений по H2 — `k/128`. Измерения показывают, что даже при высокой загрузке k < 32, то есть **менее 1/8 ложного сравнения ключей на один поиск**.

## Map Assign

`runtime_mapassign` — это функция, которую компилятор вызывает на **запись** `m[key] = value`. Важнейший момент сразу: она **не записывает значение сама**. Она находит/создаёт слот для ключа и **возвращает указатель на ячейку значения** (`elem`), а сам `value` туда уже пишет код, сгенерированный компилятором. То есть её задача — «выделить место под значение и вернуть адрес».

Разберём по шагам (`src/internal/runtime/maps/runtime_swiss.go`).

### 1. Проверки и подготовка (строки 188-212)

```go
if m == nil { panic(errNilAssign) }      // запись в nil-мапу = паника
if m.writing != 0 { fatal("concurrent map writes") }  // детект гонки

hash := typ.Hasher(key, m.seed)          // считаем хэш
m.writing ^= 1                           // ставим флаг "идёт запись"
```

Флаг `writing` ставится **после** `Hasher`, потому что хэш-функция может запаниковать (например, ключ — несравнимый тип), и тогда записи фактически не было.

### 2. Ленивая инициализация и small-путь (строки 214-232)

```go
if m.dirPtr == nil {
    m.growToSmall(typ)      // первая вставка: аллоцируем одну группу
}

if m.dirLen == 0 {          // маленькая мапа
    if m.used < abi.SwissMapGroupSlots {   // < 8
        elem := m.putSlotSmall(typ, hash, key)  // кладём в единственную группу
        m.writing ^= 1
        return elem
    }
    m.growToTable(typ)      // 9-й элемент → превращаем в полноразмерную мапу
}
```

Пока ≤ 8 элементов — простой путь через один group, без директории и пробирования.

### 3. Основной цикл — поиск/вставка в таблице (строки 235-251)

```go
outer:
for {
    idx := m.directoryIndex(hash)   // верхние биты хэша → таблица
    t := m.directoryAt(idx)
    seq := makeProbeSeq(h1(hash), t.groups.lengthMask)  // старт probe sequence

    var firstDeletedGroup groupReference  // запоминаем первый tombstone
    var firstDeletedSlot uintptr

    for ; ; seq = seq.next() {           // идём по группам (пробирование)
        g := t.groups.group(typ, seq.offset)
        match := g.ctrls().matchH2(h2(hash))  // ищем H2 во всех 8 слотах сразу
```

`outer` — внешний цикл с меткой, нужен чтобы после `rehash` начать **всё заново**: таблица сменилась, и даже индекс каталога мог измениться (при расщеплении с ростом каталога).

### 4. Случай A — ключ уже существует (обновление) (строки 254-276)

```go
for match != 0 {
    i := match.first()
    slotKey := g.key(typ, i)
    if typ.Key.Equal(key, slotKey) {     // нашли тот же ключ
        if typ.NeedKeyUpdate() {
            typedmemmove(typ.Key, slotKey, key)  // обновим ключ (для float и т.п.)
        }
        slotElem = ... // адрес значения
        break outer    // возвращаем адрес — значение перезапишет компилятор
    }
    match = match.removeFirst()
}
```

`matchH2` мог дать ложное совпадение (совпали 7 бит H2, но ключи разные), поэтому **обязательна** полная сверка `Key.Equal`.

`NeedKeyUpdate` нужен там, где «равные» ключи различимы: например, `+0.0` и `-0.0` для float сравниваются как равные, но при перезаписи `m[-0.0] = x` в карте должен остаться новый ключ.

### 5. Случай B — ключа нет, нашли пустой слот → вставка (строки 280-327)

```go
match = g.ctrls().matchEmpty()
if match != 0 {                  // конец probe sequence — ключа точно нет
    var i uintptr
    if firstDeletedGroup.data != nil {
        // если по пути попался tombstone — переиспользуем его (экономим место)
        g = firstDeletedGroup
        i = firstDeletedSlot
        t.growthLeft++           // компенсируем декремент ниже
    } else {
        i = match.first()        // иначе берём пустой слот
    }

    if t.growthLeft > 0 {        // есть место → вставляем
        ... typedmemmove(typ.Key, slotKey, key)  // копируем ключ
        g.ctrls().set(i, ctrl(h2(hash)))         // помечаем слот занятым (H2)
        t.growthLeft--
        t.used++
        m.used++
        break outer
    }

    t.rehash(typ, m)             // места нет → удвоение или расщепление таблицы
    continue outer               // и начинаем поиск заново
}
```

Здесь видно зачем нужны пустые слоты: `matchEmpty()` — это сигнал «дошли до конца цепочки, ключа нет, можно вставлять». А `growthLeft == 0` запускает `rehash`: удвоение ёмкости таблицы, если результат ≤ 1024, иначе расщепление на две таблицы (с возможным удвоением каталога).

> Отличие от `table.PutSlot` (`table.go:329-332`) и быстрых путей: там перед ростом сначала вызывается `t.pruneTombstones(typ, m)`, и рост происходит только если pruning не помог. В обобщённом `runtime_mapassign` этого шага нет.

### 6. Случай C — группа полна, есть tombstone (строки 334-342)

```go
if firstDeletedGroup.data == nil {
    match = g.ctrls().matchEmptyOrDeleted()  // тут только deleted (empty проверили выше)
    if match != 0 {
        firstDeletedGroup = g    // запомнили первый tombstone и идём дальше
        firstDeletedSlot = match.first()
    }
}
```

Если в группе нет ни ключа, ни пустого слота, но есть **tombstone** (удалённый элемент) — запоминаем его как кандидата. Но **сразу не вставляем** — сначала надо до конца пройти probe sequence, вдруг ключ уже существует дальше по цепочке (тогда это апдейт, а не вставка). Если ключа так и не нашлось, вставку сделаем в запомненный tombstone (случай B).

### 7. Завершение (строки 346-352)

```go
if m.writing == 0 { fatal("concurrent map writes") }
m.writing ^= 1       // снимаем флаг записи
return slotElem      // возвращаем адрес ячейки значения
```

### Главное, что нужно понять

**`mapassign` возвращает указатель, а не пишет значение.** Поэтому `m[k] = v` компилируется примерно в:

```go
ptr := runtime.mapassign(typ, m, &k)
*ptr = v   // ← вот это пишет уже сгенерированный компилятором код
```

Это позволяет:

- единообразно обрабатывать и вставку, и обновление (в обоих случаях нужен адрес слота);
- избегать лишнего копирования значения внутри рантайма;
- поддерживать `m[k].field = ...` и операции вроде `m[k]++`.

### Карта приоритетов вставки

```
идём по probe sequence:
  ├─ нашли тот же ключ        → обновление (случай A)
  ├─ нашли tombstone          → запомнили, идём дальше (случай C)
  └─ нашли пустой слот (стоп) → вставка:
        ├─ был tombstone?     → вставляем в него (переиспользуем)
        ├─ есть growthLeft?   → вставляем в пустой
        └─ места нет          → [pruneTombstones, кроме runtime_mapassign]
                                 rehash (удвоение / split) + начать заново
```

## Практические следствия

- **Указатели на элементы карты по-прежнему брать нельзя.** Любая вставка может вызвать `rehash`, который переносит все записи в новую аллокацию. Адрес, который вернул `mapassign`, валиден только до следующей модификации карты.
- **Порядок итерации рандомизирован дважды** (стартовый слот + стартовая таблица) и вдобавок сид хеша уникален для каждой карты. Полагаться на порядок нельзя ни при каких размерах — даже на 8 элементах.
- **`make(map[K]V, n)` действительно работает**: ёмкость считается с поправкой `8/7`, каталог и таблицы создаются сразу.
- **Массовое удаление не освобождает память.** Слоты становятся tombstone, `capacity` не уменьшается, каталог не сжимается. Освобождение произойдёт только при следующем росте (rehash отбрасывает старые группы) или при пересоздании карты. `pruneTombstones` возвращает ёмкость под вставки, но не отдаёт память.
- **Малые карты (≤ 8) — совсем другой код.** Ни каталога, ни пробирования, ни tombstone. Если микробенчмарк на 8 элементах показал одно, а на 10 тысячах — другое, это ожидаемо.
- **Максимальная задержка одной вставки ограничена** переносом 1024 записей, а не размером всей карты.
